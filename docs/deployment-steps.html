End-to-End Deployment Steps

Use this as the single sequence for professors and staff supporting class teams. It combines local setup, integration, CI/CD, and production validation into one ordered process.

Never done this before? That's fine. Each step says what it does, why, and how you can tell it worked. Unfamiliar words are explained in the Glossary.

WVU note: If cloud resources are missing, submit a request to Statler ITS for resource group and access support before continuing.

Step-by-Step Runbook

Follow these steps in order. If a step fails, resolve it before moving ahead so later cloud checks are based on a known-good state.

  1. Confirm the team has the required software: Node.js 24 LTS, Git, VS Code, and Azure/GitHub access.
  2. Confirm the WVU resource group and Azure resources exist (request via Statler ITS if needed).
  3. Clone the repository and verify its structure (frontend/, backend/, .github/workflows/).
  4. Set up the backend locally: npm install, backend/.env, database schema, npm run dev.
  5. Set up the frontend locally: npm install, frontend/.env, npm run dev.
  6. Verify registration, login, refresh, and logout work locally.
  7. Validate the Sprint 3 data path: choose a month, Fetch Data, see the map fill in.
  8. Add the GitHub secrets and variables (see GitHub Setup).
  9. Set the App Service environment variables, deploy the backend, and verify /health.
  10. Deploy the frontend through GitHub Actions.
  11. Perform end-to-end production tests: login, refresh, map fetch, logout, and backend requests in the browser's network tools.

Per-Semester Setup of the Reference Deployment

The reference app is the finished example that students are shown. Its Azure resources are deleted at the end of each semester to save money and rebuilt at the start of the next. This section rebuilds them from nothing. Allow about an hour, most of it Azure thinking. Every value you need is spelled out. If a word is new, the Glossary explains it.

Watch the sizes, because they cost money. Some of what you create is billed by the hour for as long as it exists. The portal's default choices are far larger, and more expensive, than this project needs. Use exactly the sizes named below: App Service plan Basic B1, Static Web App Free, MySQL Standard_B1ms. Check current prices on Azure's pricing pages.

Doing a whole class? The Azure Scripts page creates the servers, backends, and frontends for every group in one go. The steps below show what those scripts do, so you understand each piece.

  1. Get the resource group. A resource group is the folder that holds the demo's Azure resources. WVU doesn't let teams create their own, so ask Statler ITS for one named like <term>-CS330-<section>-<crn>-DEMO, for example 202608-CS330-001-84715-DEMO.
    You know it worked when the name appears in the Azure portal under Resource groups.
  2. Create the MySQL server (it stores the users). In the portal: Azure Database for MySQL flexible servers → Create. Use your resource group, a name such as xpostforecast-db, region East US, admin user mysqladmin, and size Standard_B1ms (under the Burstable compute tier). Choose MySQL version 8.x and Public access as the connectivity method. These names are examples; the scripts use a <resource group>-mysql-db pattern instead. Either works, as long as you use the same names everywhere. Choose a strong password, save it in a password manager, and don't reuse it anywhere. Then open the server's Networking page and:
    • Tick Allow public access from any Azure service within Azure to this server. Without this, the backend (an Azure service) can't reach the database.
    • Add your own IP address with Add current client IP address, then Save. This lets your computer connect. Never add the "0.0.0.0 - 255.255.255.255" range, which opens the database to the whole internet.
    Next create the table the app needs (the database schema): open the server's Connect page, click Cloud Shell, run the mysql command it shows (you will be asked for the password), then paste the whole contents of backend/db/schema.sql at the mysql> prompt. Cloud Shell runs inside Azure, so it needs no rule for your own IP address, but it does depend on the Allow public access from any Azure service tick-box above.
    You know it worked when USE authdb; SHOW TABLES; lists a table named users.
  3. Create the backend (an App Service). This is where the Node.js server will run. Create it with the command line, not the portal's form. The form picks an expensive default size, gives the app an address with a random suffix (which breaks every address in these docs), and leaves publishing switched off. Click the >_ icon at the top of the portal to open Cloud Shell (choose Bash), and run these three commands, replacing the three names in angle brackets: 
    az appservice plan create --resource-group <resource-group> --name <plan-name> --is-linux --sku B1 --location eastus
az webapp create --resource-group <resource-group> --plan <plan-name> --name <app-name> --runtime "NODE:24-lts"
az resource update --resource-group <resource-group> --namespace Microsoft.Web --resource-type basicPublishingCredentialsPolicies --parent sites/<app-name> --name scm --set properties.allow=true
    • Before you start: Cloud Shell uses your default subscription. Check it with az account show --query name -o tsv. It should be the WVU course subscription (for example ind-statler-mhseery). Change it with az account set --subscription "<name>". If Cloud Shell offers storage options the first time, choose No storage account required; nothing here needs saved files. App names are unique across all of Azure, so if yours is taken, add your initials.
    • The first creates the rented computer (Basic B1, Linux). The second creates the app on it using Node 24 LTS, matching the workflows. The third switches on publishing credentials; without it the Download publish profile button is greyed out.
    • Example names: plan 202608-cs330-demo-plan, app 202608-cs330-demo-backend.
    • If you reuse an existing plan, skip the first command and use that plan's name in the second.
    You know it worked when https://<app-name>.azurewebsites.net shows Azure's "Your web app is running" page. If you must use the portal form instead, pick Basic B1 (not Premium), turn on Basic authentication on its Deployment tab, and afterwards copy the real address from the app's Overview → Default domain, since it will have a random suffix.
  4. Create the frontend (a Static Web App). This hosts the website files. Portal: Static Web Apps → Create. Use your resource group, a name such as 202608-cs330-demo-frontend, plan type Free (the form defaults to a paid plan), and deployment source Other. "Other" matters: with "GitHub" Azure adds its own workflow file to your repository and the two would fight.
    You know it worked when the app's Overview page shows a URL ending in .azurestaticapps.net and the status Waiting for deployment. Copy that URL; you need it in the next step.
  5. Give the backend its settings. A program shouldn't have its database address or passwords written inside it, so Azure hands them over as settings when it starts. On the app: Settings → Environment variables → App settings, add the eight below, then click Apply (the app restarts). The six that aren't secret can be set in one command in Cloud Shell: 
    az webapp config appsettings set --resource-group <resource-group> --name <app-name> --settings DB_HOST=<server>.mysql.database.azure.com DB_USER=mysqladmin DB_NAME=authdb DB_PORT=3306 NODE_ENV=production FRONTEND_URL=https://<static-web-app-url-without-slash>
    SettingValueWhy
    DB_HOST<server>.mysql.database.azure.comWhere the database is.
    DB_USERmysqladminThe database login name.
    DB_PASSWORDThe password from step 2 (add in the portal)The database login password. Must be named exactly this.
    DB_NAMEauthdbWhich database holds the users table.
    DB_PORT3306MySQL's standard port.
    FRONTEND_URLhttps:// + the Static Web App URL, with no slash at the endThe only website allowed to call the backend (CORS). A wrong value makes logins fail in the browser.
    JWT_SECRETA new random value (add in the portal), see belowThe key that signs login cookies. Anyone who has it can forge a login, so use a different one from your laptop's.
    NODE_ENVproductionSwitches on the cookie settings that cross-site login needs.
    Make a JWT_SECRET by running this on your own computer (Node 24) and pasting the result, without any spaces: 
    node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
    Do not add a PORT setting. Azure chooses the port itself and the app obeys it.
  6. Give GitHub permission to deploy. The deploy workflows need three secrets and two variables in the repository (Settings → Secrets and variables → Actions; only a repository Admin can see Settings). Names must match exactly, capitals included. Full details are on GitHub Setup.
    NameKindValue and where it comes from
    APP_SERVICE_PUBLISH_PROFILESecretBackend app → Overview → Download publish profile; paste the whole file contents.
    AZURE_STATIC_WEB_APPS_API_TOKENSecretStatic Web App → Overview → Manage deployment token → copy.
    VITE_BACKEND_API_URLSecrethttps:// + the backend's Default domain from its Overview page, no slash at the end.
    AZURE_WEBAPP_NAMEVariableThe backend app's name, for example 202608-cs330-demo-backend.
    DEPLOY_TO_AZUREVariabletrue. Set it last, once the others exist.
    Old secrets from last semester are left behind in the repository and keep their old values. Replace them; don't add duplicates with slightly different names.
  7. Deploy. In the repository's Actions tab, choose Deploy backend (App Service), click Run workflow, and wait for the green check (about a minute). Then do the same for Deploy frontend (Static Web Apps). Running them by hand means you don't have to push a fake change.
    You know it worked when both show a green check. If one is red, open it, click the red step, and read the last lines; the Troubleshooting page lists the usual causes.
  8. Check the live site with the next section, then the Final Acceptance Checklist at the bottom of the page.

At the end of the semester, after the resources are deleted (the Remove script does it), set DEPLOY_TO_AZURE to false so the deploy workflows show as skipped instead of failing, and delete the three Azure secrets so stale credentials don't linger in the repository settings.

Check the live site yourself

A green workflow only proves that files were uploaded. These checks prove the pieces work together. Run the commands in Cloud Shell, in Bash mode. The toolbar at the top-left of Cloud Shell shows "Switch to PowerShell" when you are in Bash; if it says "Switch to Bash", click it. These are Bash commands and will not run in PowerShell. Replace the two addresses with your own. 

BACKEND=https://<backend default domain>
SITE=https://<static web app url>

# 1. Is the backend alive?
curl -s -w "\nHTTP %{http_code}\n" $BACKEND/health

# 2. Will the backend accept calls from the website? (the browser asks this before logging in)
curl -s -i -X OPTIONS $BACKEND/auth/login -H "Origin: $SITE" -H "Access-Control-Request-Method: POST" | grep -i -E "^HTTP|access-control-allow"

# 3. Can the backend reach the database? (a made-up user must get a clean "wrong credentials", not a crash)
curl -s -w "\nHTTP %{http_code}\n" -X POST $BACKEND/auth/login -H "Content-Type: application/json" -d '{"username":"nobody-here","password":"not-a-real-password"}'

# 4. Does the website send the right headers, and does refreshing /map work?
curl -s -I $SITE/ | grep -i referrer-policy
curl -s -o /dev/null -w "HTTP %{http_code}\n" $SITE/map
CheckGood resultIf not
1. /health {"ok":true,"env":"production"} and HTTP 200 The first request after a deploy can take a minute or more (a cold start); try again. "env":"development" means NODE_ENV isn't set. Still failing: open the app's Monitoring → Log stream.
2. CORS HTTP 204 and Access-Control-Allow-Origin equal to your website's address, plus Access-Control-Allow-Credentials: true The address differs from FRONTEND_URL (a slash, http vs https, or a typo). Fix the setting and Apply.
3. Database HTTP 401 and {"error":"Invalid credentials"}. The 401 means the app asked the database and got "no such user". HTTP 429 means you have run this check too many times (the limit is 20 login attempts per 15 minutes per address): wait 15 minutes. HTTP 500 means the database couldn't be reached: check DB_* settings, the password, and that "Allow public access from any Azure service" is ticked.
4. Website Referrer-Policy: strict-origin-when-cross-origin and /map returns HTTP 200 Missing header: redeploy the frontend. A 404 on /map: staticwebapp.config.json isn't in frontend/public/.

Anything that involves a real password has to be done by a person in a browser, so finish with a hands-on pass on the live site (the Final Acceptance Checklist below spells out the same things). Use a throwaway password you don't use anywhere else:

  1. Open the Static Web App URL and open the browser's developer tools (F12 → Console). The line Frontend API Base URL: … should show your Azure backend, not localhost.
  2. Register a test account, then log in. You should land on the map page.
  3. Pick a month and click Fetch Data. A coloured temperature layer should appear on top of a real street map. Grey squares saying "Access blocked" mean the map-tile problem on the Troubleshooting page.
  4. Refresh the page while on /map. You should stay logged in and see the map again.
  5. Log out. You should return to the login page, and visiting /map should send you back to log in.

Temperature data needs a login on purpose, so a plain web request to /temperature/… without logging in correctly returns HTTP 401.

Critical Deployment Checks

Use this section as a quick side-by-side review when a deployment succeeds in one layer but fails in the other. Most production issues come from one missed setting in these lists.

Backend (App Service)

  • Workflow paths use backend
  • APP_SERVICE_PUBLISH_PROFILE secret and AZURE_WEBAPP_NAME variable are present
  • Runtime is Node 24 LTS; PORT is not set by hand
  • The address used for VITE_BACKEND_API_URL was copied from the app's Default domain, not guessed
  • App settings contain DB, JWT, FRONTEND_URL, and NODE_ENV=production
  • /health returns {"ok":true,"env":"production"}

Frontend (Static Web App)

  • The deploy step uploads frontend/dist (or, in an Azure-generated workflow, app_location: "frontend" with output_location: "dist")
  • VITE_BACKEND_API_URL is provided to the build
  • staticwebapp.config.json is in frontend/public/ (it fixes page refreshes and sets Referrer-Policy)
  • Build and tests succeed in GitHub Actions
  • Browser console shows the Azure backend as Frontend API Base URL

Final Acceptance Checklist

Consider the deployment complete only after all items below are true in the live environment, not just in local development.

  • Frontend site loads at the SWA URL without errors in the console.
  • Users can register and log in using the production backend.
  • Refreshing on /map keeps the user logged in (no 404, no redirect to login).
  • Temperature data requests return points and the map shows the coloured layer on top of a real street map (no grey "Access blocked" squares).
  • Logout returns to the login page, and /map then redirects to login.
  • No CORS errors in the browser console.
  • The App Service log stream shows no startup crashes or database connection failures.
  • The first /health request after a deploy may be slow (a cold start); the second answers quickly with {"ok":true,"env":"production"}.
