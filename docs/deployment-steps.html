End-to-End Deployment Steps

Use this as the single sequence for professors and staff supporting class teams. It combines local setup, integration, CI/CD, and production validation into one ordered process.

WVU note: If cloud resources are missing, submit a request to Statler ITS for resource group and access support before continuing.

Step-by-Step Runbook

Follow these steps in order. If a step fails, resolve it before moving ahead so later cloud checks are based on a known-good state.

  1. Confirm the team has the required software: Node.js 24 LTS, Git, VS Code with the SQLTools extensions, and Azure/GitHub access.
  2. Confirm the WVU resource group and Azure resources exist (request via Statler ITS if needed).
  3. Clone the repository and verify its structure (frontend/, backend/, .github/workflows/).
  4. Set up the backend locally: npm install, backend/.env, database schema, npm run dev.
  5. Set up the frontend locally: npm install, frontend/.env, npm run dev.
  6. Verify registration, login, refresh, and logout work locally.
  7. Validate the Sprint 3 data path: choose a month, Fetch Data, see the map fill in.
  8. Add the GitHub secrets and variable (see GitHub Setup).
  9. Set the App Service environment variables, deploy the backend, and verify /health.
  10. Deploy the frontend through GitHub Actions.
  11. Perform end-to-end production tests: login, refresh, map fetch, logout, and backend requests in the browser's network tools.

Per-Semester Setup of the Reference Deployment

The reference app's Azure resources are torn down and rebuilt each semester. To bring the demo back up:

  1. Request the resource group through Statler ITS.
  2. MySQL Flexible Server: create it; in Networking add your IP and enable access from Azure services. Run backend/db/schema.sql with SQLTools.
  3. App Service: Web App, Linux, runtime Node 24 LTS. Turn on SCM Basic Auth Publishing Credentials (Configuration → General settings), then Download publish profile.
  4. Static Web App: deployment source Other (so Azure doesn't commit its own workflow to the repo). Copy the token from Manage deployment token.
  5. App Service environment variables: the eight settings on Azure Basics, with FRONTEND_URL set to the new SWA URL and a fresh JWT_SECRET.
  6. GitHub (Settings → Secrets and variables → Actions): replace APP_SERVICE_PUBLISH_PROFILE, AZURE_STATIC_WEB_APPS_API_TOKEN, and VITE_BACKEND_API_URL; set the variables AZURE_WEBAPP_NAME and DEPLOY_TO_AZURE = true.
  7. Deploy: Actions → run Deploy backend (App Service), then Deploy frontend (Static Web Apps).
  8. Work through the Final Acceptance Checklist below.

At the end of the semester, after the resources are deleted, set DEPLOY_TO_AZURE to false (deploy workflows then show as skipped instead of failing) and delete those secrets so stale credentials don't linger in the repository settings.

Commands Used Most Often

These are the core commands used during setup and redeployment. If you cloned https://github.com/tdevine1/xPostForecast, these paths work as written on every branch. If you are using your own repository, update folder paths to match your project structure. 

# Backend local run
cd backend
npm install
npm run dev

# Frontend local run (second terminal)
cd frontend
npm install
npm run dev

# Run the checks CI runs
npm run lint
npm test

# Trigger cloud deployment
git add .
git commit -m "Deploy updates"
git push origin main

Critical Deployment Checks

Use this section as a quick side-by-side review when a deployment succeeds in one layer but fails in the other. Most production issues come from one missed setting in these lists.

Backend (App Service)

  • Workflow paths use backend
  • APP_SERVICE_PUBLISH_PROFILE secret and AZURE_WEBAPP_NAME variable are present
  • Runtime is Node 24 LTS; PORT is not set by hand
  • App settings contain DB, JWT, FRONTEND_URL, and NODE_ENV=production
  • /health returns {"ok":true,"env":"production"}

Frontend (Static Web App)

  • The deploy step uploads frontend/dist (or, in an Azure-generated workflow, app_location: "frontend" with output_location: "dist")
  • VITE_BACKEND_API_URL is provided to the build
  • staticwebapp.config.json is in frontend/public/
  • Build and tests succeed in GitHub Actions
  • Browser console shows the Azure backend as Frontend API Base URL

Final Acceptance Checklist

Consider the deployment complete only after all items below are true in the live environment, not just in local development.

  • Frontend site loads at the SWA URL without errors in the console.
  • Users can register and log in using the production backend.
  • Refreshing on /map keeps the user logged in (no 404, no redirect to login).
  • Temperature data requests return points and the map renders markers.
  • Logout returns to the login page, and /map then redirects to login.
  • No CORS errors in the browser console.
  • The App Service log stream shows no startup crashes or database connection failures.
