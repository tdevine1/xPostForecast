Getting Started

This page is the starting point for WVU professors and staff. It combines Sprint 1 through Sprint 3 setup details into one clear foundation before cloud deployment.

WVU resource group process: At WVU, project teams request Azure resource group setup through Statler ITS. Do this first so deployment resources are available.
Next: GitHub Setup

Prerequisites

Before you begin, make sure each person supporting the course has both local developer tooling and the correct cloud/repository access. Most deployment blockers come from missing permissions.

  • Node.js 24 LTS and npm (current Vite releases don't run on older Node versions)
  • Git
  • VS Code
  • VS Code extensions SQLTools (Matheus Teixeira) and SQLTools MySQL/MariaDB/TiDB; the repo's .vscode/extensions.json recommends both
  • GitHub repository access for your course project
  • Azure access details from instructor or WVU support staff

Choose Your Starting Path

You can either clone the course reference repository directly or follow the same documentation for your own project repository. Both paths work, but cloning the reference project is the fastest way for new staff to practice the full deployment sequence.

Option A: Clone xPostForecast (recommended)

Use this if you want the exact reference structure used in class documentation.

git clone https://github.com/tdevine1/xPostForecast.git
cd xPostForecast

# main is the finished app (Sprint 4); each earlier sprint is a branch
git switch sprint-2      # look at the app as it was at the end of Sprint 2
git switch main          # back to the finished app

Option B: Use your own project

Use this if your class team already has a separate repo. Keep the same architecture pattern: React frontend, Node/Express backend, MySQL database, and Azure deployment targets.

You can still follow every page in this guide; just adapt folder paths to your repository layout. Keep the environment variable names exactly as shown here, since the code reads them by name.

Reference Architecture

The project is intentionally split so each layer can be tested independently. Frontend issues, backend issues, and database issues can be isolated quickly when this structure is preserved.

Frontend

  • React + Vite app
  • Login/register pages and map page
  • Axios client in src/api.js
  • Leaflet map for WV temperature points

Backend and Data

  • Node.js + Express backend
  • JWT auth in HTTP-only cookies
  • Azure Database for MySQL over TLS (CA certificate in the repo)
  • STAC data pipeline from Planetary Computer

Initial Local Setup

The sequence below assumes you are validating that the app works locally before cloud deployment. Completing this successfully prevents most CI/CD failures later.

  1. Clone the project repository and open it in VS Code.
  2. Allow your public IP address in the Azure MySQL server's Networking firewall rules.
  3. Install backend dependencies and create backend/.env from .env.example.
  4. Connect to Azure MySQL with SQLTools (SSL enabled, CA file backend/config/DigiCertGlobalRootG2.crt.pem, a Password mode other than plaintext), run backend/db/schema.sql, then run the backend.
  5. Install frontend dependencies, create frontend/.env, run Vite, and test the login flow.
# Example using the reference repository (main branch)
git clone https://github.com/tdevine1/xPostForecast.git
cd xPostForecast

# backend
cd backend
npm install
cp .env.example .env          # then fill in the values (table below)
# create the schema: open db/schema.sql in VS Code, select all, run with SQLTools (Ctrl+E Ctrl+E)
npm run dev                   # http://localhost:5175

# frontend (in another terminal, from the repository root)
cd frontend
npm install
cp .env.example .env          # VITE_BACKEND_API_URL=http://localhost:5175
npm run dev                   # http://localhost:5173

Backend Environment Variables (Local)

These are the exact names the code reads (see backend/.env.example). A small naming difference such as DB_PASS instead of DB_PASSWORD is a common source of configuration bugs; the backend refuses to start and lists any required variable that is missing.

Variable Purpose
DB_HOST Azure MySQL host, usually <server>.mysql.database.azure.com
DB_USER, DB_PASSWORD Database credentials
DB_NAME Database name (authdb in the reference app)
DB_PORT 3306 (the default if unset)
FRONTEND_URL Local frontend origin, http://localhost:5173
JWT_SECRET JWT signing secret; generate with node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
NODE_ENV development locally; production on Azure
PORT 5175 locally; set automatically on Azure App Service

SQLTools and Database Passwords

SQLTools saves each connection in the project's .vscode/settings.json. With Password mode Save as plaintext in settings, the database password is written into that file, and a committed copy stays in the git history even after the file is deleted. This reference repository leaked a database password exactly that way once, which makes it a useful example for students.

  • Use Password mode SQLTools Driver Credentials (the default, stored in VS Code's secure storage) or Ask on connect.
  • Keep .vscode/settings.json out of git with .vscode/* and !.vscode/extensions.json in .gitignore, as this repo does.
  • If a password is ever pushed, change it in Azure first, then clean up the repository.

Database Bootstrap SQL

The schema is in backend/db/schema.sql (run it with SQLTools as described above). It contains:

CREATE DATABASE IF NOT EXISTS authdb;
USE authdb;

CREATE TABLE IF NOT EXISTS users (
  id INT AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(255) NOT NULL UNIQUE,
  username VARCHAR(255) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

Minimum Validation Before Cloud Work

Treat this as a gate: if any item below fails locally, pause and fix it before moving to GitHub Actions or Azure deployment. This saves significant debugging time in production.

  • Frontend loads on http://localhost:5173.
  • Backend prints Successfully connected to MySQL and http://localhost:5175/health responds.
  • Register, log in, and refresh the page: you stay logged in.
  • Fetch Data draws temperatures on the map (any month from 1895 to September 2022).
  • npm test passes in both frontend/ and backend/.
