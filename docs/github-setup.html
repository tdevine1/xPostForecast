GitHub Setup

This page combines the repository, secrets, and GitHub Actions requirements from the Sprint 4 guides so faculty and staff can verify the CI/CD pipeline configuration in one place.

Next: Azure Basics

Repository Baseline

Start by confirming how your team will track changes. Most deployment problems in class come from paths, secret names, or files that should never have been committed.

  • Confirm instructors, staff, and project teams all have the correct repo permissions.
  • Use main as the deployment branch: both deploy workflows run on pushes to main.
  • Ensure .gitignore excludes .env, node_modules, and dist; check git status before every commit.
  • Use pull requests for larger changes: the CI workflow tests every push and pull request.
# Standard update cycle
git status                      # nothing like .env or node_modules listed?
git add .
git commit -m "Describe the change"
git push origin main            # triggers CI, and deployment if frontend/ or backend/ changed

Workflows in the Reference Repository

FileRuns whenDoes
ci.yml Every push and pull request, on every branch Lint, test, and build the frontend; lint and test the backend
deploy-backend.yml Push to main changing backend/, or manually Install, test, remove dev packages, deploy backend/ to App Service
deploy-frontend.yml Push to main changing frontend/, or manually Install, test, build with VITE_BACKEND_API_URL, upload frontend/dist to Static Web Apps

"Manually" means Actions → choose the workflow → Run workflow, which is handy right after setting up new Azure resources.

Required GitHub Secrets and Variables

Secrets are required because Azure deployments need credentials that must never be committed to source control. Add them under Settings → Secrets and variables → Actions.

Name Kind Used By Value
APP_SERVICE_PUBLISH_PROFILE Secret deploy-backend.yml Full XML contents of the App Service publish profile
AZURE_WEBAPP_NAME Variable deploy-backend.yml The App Service's name
VITE_BACKEND_API_URL Secret deploy-frontend.yml build step https://<backend-app>.azurewebsites.net (no trailing slash)
AZURE_STATIC_WEB_APPS_API_TOKEN Secret deploy-frontend.yml From the Static Web App's Manage deployment token

Both deploy workflows check for these first and fail with a clear message naming anything that is missing.

Student repositories: if you connect a group's Static Web App to their GitHub repo in the Azure Portal, Azure commits its own workflow (azure-static-web-apps-<name>.yml) and creates a secret named AZURE_STATIC_WEB_APPS_API_TOKEN_<NAME>. That's option A in the student guide; students then only add VITE_BACKEND_API_URL and fix app_location.

Backend Workflow Checks

For .github/workflows/deploy-backend.yml, verify:

  • working-directory, cache-dependency-path, and package all point to backend.
  • The deploy step uses vars.AZURE_WEBAPP_NAME and secrets.APP_SERVICE_PUBLISH_PROFILE.
  • node-version is 24, matching the App Service runtime.
  • The test script runs real tests. npm's default placeholder script exits with an error and blocks every deployment.
- run: npm ci
- run: npm test
- name: Remove dev-only packages before upload
  run: npm prune --omit=dev
- name: Deploy to Azure App Service
  uses: azure/webapps-deploy@v3
  with:
    app-name: ${{ vars.AZURE_WEBAPP_NAME }}
    publish-profile: ${{ secrets.APP_SERVICE_PUBLISH_PROFILE }}
    package: backend

Frontend SWA Workflow Checks

The reference repo builds the frontend inside its own workflow and uploads the finished site. Check that the build receives the backend URL and the upload points at the build output: 

- name: Build
  run: npm run build
  env:
    VITE_BACKEND_API_URL: ${{ secrets.VITE_BACKEND_API_URL }}

- name: Deploy to Azure Static Web Apps
  uses: Azure/static-web-apps-deploy@v1
  with:
    azure_static_web_apps_api_token: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN }}
    action: upload
    app_location: frontend/dist
    skip_app_build: true

For an Azure-generated workflow in a student repo (option A), check instead:

  • app_location: "frontend", api_location: "", output_location: "dist"
  • An env: block on the deploy step maps VITE_BACKEND_API_URL from secrets
  • close_pull_request_job has the same app_location if YAML validation requires it
  • Only one workflow deploys the frontend

Either way, frontend/public/staticwebapp.config.json must exist so refreshing a page such as /map doesn't return 404.

Deployment Trigger and Monitoring

After pushing changes, use GitHub Actions as your first diagnostics layer. A green workflow usually means the problem is in runtime configuration, while a red workflow usually means a path, script, test, or secret issue.

  1. Push a commit to main (or run a deploy workflow manually).
  2. Open GitHub Actions and watch the CI and deploy workflows.
  3. Confirm the settings check, test, build, and deploy steps are green.
  4. If something failed, open the step's log and use the troubleshooting page in this site.
Security reminder: Never commit publish profiles, deployment tokens, or any .env file. Editor settings that store database passwords (for example SQLTools connections in .vscode/settings.json) count too.
