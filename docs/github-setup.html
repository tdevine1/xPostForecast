GitHub Setup

This page combines the repository, secrets, and GitHub Actions requirements from the Sprint 4 guides so faculty and staff can verify the CI/CD pipeline configuration in one place.

If this is your first time with GitHub Actions: a workflow is a set of written instructions that makes GitHub test and deploy the project automatically whenever code is pushed. A secret is a hidden password the workflow needs. Both are explained in the Glossary, and students are taught to write their own in the student workflows guide.

Repository Baseline

Start by confirming how your team will track changes. Most deployment problems in class come from paths, secret names, or files that should never have been committed.

  • Confirm instructors, staff, and project teams all have the correct repo permissions. Follow the principle of least privilege: give each person only the access they need. Write lets someone push code and use the workflows. Admin can also open Settings, add or read secrets' names, change who has access, and delete the repository, so keep it to one person per team (and the instructor). Every team member must be added to the repo so commits are made under their own account.
  • Use main as the deployment branch: both deploy workflows run on pushes to main.
  • Ensure .gitignore excludes .env, node_modules, dist, .vscode/* (except extensions.json), and *.PublishSettings; check git status before every commit.
  • Use pull requests for larger changes: the CI workflow tests every push and pull request.
# Standard update cycle
git status                      # nothing like .env or node_modules listed?
git add .
git commit -m "Describe the change"
git push origin main            # triggers CI, and deployment if frontend/ or backend/ changed

Workflows in the Reference Repository

FileRuns whenDoes
ci.yml Every push and pull request, on every branch Lint, test, and build the frontend; lint and test the backend. A third job, sonar, sends code quality and coverage to SonarQube Cloud, and only runs when SONAR_ENABLED is true
deploy-backend.yml Push to main changing backend/, or manually Install, test, remove dev packages, deploy backend/ to App Service
deploy-frontend.yml Push to main changing frontend/, or manually Install, test, build with VITE_BACKEND_API_URL, upload frontend/dist to Static Web Apps

"Manually" means Actions → choose the workflow → Run workflow, which is handy right after setting up new Azure resources.

Required GitHub Secrets and Variables

Azure deployments need credentials, and credentials must never be committed to source control, because anything pushed to GitHub is as good as public. GitHub therefore keeps them in two places outside your code. Add both under Settings → Secrets and variables → Actions, on the Secrets tab or the Variables tab. Only a repository Admin can see the Settings tab.

Secret

Hidden and encrypted. After saving, nobody can read it again, and GitHub blanks it out of logs. Use for anything that works like a password.

Variable

Visible to anyone with access. Use for settings that are not sensitive, such as an app's name or an on/off switch.

Names must match the workflow files exactly, including capital letters. A name that is one letter off is simply a different setting, and the workflow can't see it.

Name Kind Used By Value
DEPLOY_TO_AZURE Variable Both deploy workflows true while this semester's Azure resources exist; anything else skips deployment
APP_SERVICE_PUBLISH_PROFILE Secret deploy-backend.yml Full contents of the App Service publish profile: in the Azure portal open the App Service, click Overview → Download publish profile, open the downloaded file in a text editor, and copy all of it. Delete the downloaded file afterwards.
AZURE_WEBAPP_NAME Variable deploy-backend.yml The App Service's name
VITE_BACKEND_API_URL Secret deploy-frontend.yml build step https:// + the backend's Default domain, copied from the App Service Overview page, with no slash at the end. Copy it; don't type it from memory, because apps made in the portal have a random suffix.
AZURE_STATIC_WEB_APPS_API_TOKEN Secret deploy-frontend.yml In the Azure portal open the Static Web App, click Overview → Manage deployment token, and copy the token
SONAR_TOKEN Secret ci.yml sonar job From SonarQube Cloud: My Account → Access tokens → Generate Token (choose an expiry later than your project end date; the default is 30 days) (see the SonarQube guide)
SONAR_ENABLED Variable ci.yml sonar job true to turn the SonarQube job on; anything else skips it

Both deploy workflows check for these first and fail with a clear message naming anything that is missing.

Beware of leftovers from last semester. Secrets and variables stay in the repository after the Azure resources are deleted, and they keep their old values. When you set up a new semester, replace the old ones; don't add look-alikes. In particular, a secret named AZURE_STATIC_WEB_APPS_API_TOKEN_<SOMETHING> was created automatically by an earlier Azure setup, and our workflow does not read it. It needs the plain name AZURE_STATIC_WEB_APPS_API_TOKEN.
Student repositories: if you connect a group's Static Web App to their GitHub repo in the Azure Portal, Azure commits its own workflow (azure-static-web-apps-<name>.yml) and creates a secret named AZURE_STATIC_WEB_APPS_API_TOKEN_<NAME>. That's option A in the frontend guide; students then only add VITE_BACKEND_API_URL and fix app_location.

Backend Workflow Checks

For .github/workflows/deploy-backend.yml, verify:

  • working-directory, cache-dependency-path, and package all point to backend.
  • The deploy step uses vars.AZURE_WEBAPP_NAME and secrets.APP_SERVICE_PUBLISH_PROFILE.
  • In the reference repo, the job runs only when vars.DEPLOY_TO_AZURE is true; student repos don't need that line.
  • node-version is 24, matching the App Service runtime.
  • The test script runs real tests. npm's default placeholder script exits with an error and blocks every deployment.
- run: npm ci
- run: npm test
- name: Remove dev-only packages before upload
  run: npm prune --omit=dev
- name: Deploy to Azure App Service
  uses: azure/webapps-deploy@v3
  with:
    app-name: ${{ vars.AZURE_WEBAPP_NAME }}
    publish-profile: ${{ secrets.APP_SERVICE_PUBLISH_PROFILE }}
    package: backend

Frontend SWA Workflow Checks

The reference repo builds the frontend inside its own workflow and uploads the finished site. Check that the build receives the backend URL and the upload points at the build output: 

- name: Build
  run: npm run build
  env:
    VITE_BACKEND_API_URL: ${{ secrets.VITE_BACKEND_API_URL }}

- name: Deploy to Azure Static Web Apps
  uses: Azure/static-web-apps-deploy@v1
  with:
    azure_static_web_apps_api_token: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN }}
    action: upload
    app_location: frontend/dist
    skip_app_build: true

For an Azure-generated workflow in a student repo (option A), check instead:

  • app_location: "frontend", api_location: "", output_location: "dist"
  • An env: block on the deploy step maps VITE_BACKEND_API_URL from secrets
  • close_pull_request_job has the same app_location if YAML validation requires it
  • Only one workflow deploys the frontend

Either way, frontend/public/staticwebapp.config.json must exist so refreshing a page such as /map doesn't return 404.

Deployment Trigger and Monitoring

After pushing changes, use GitHub Actions as your first diagnostics layer. A green workflow usually means the problem is in runtime configuration, while a red workflow usually means a path, script, test, or secret issue.

  1. Push a commit to main (or run a deploy workflow manually).
  2. Open GitHub Actions and watch the CI and deploy workflows.
  3. Confirm the settings check, test, build, and deploy steps are green.
  4. If something failed, open the step's log and use the troubleshooting page in this site.
Security reminder: Never commit publish profiles, deployment tokens, or any .env file. Editor settings that store database passwords count too: SQLTools writes connections to .vscode/settings.json, including the password in plaintext mode, so the reference .gitignore ignores .vscode/* except extensions.json.
