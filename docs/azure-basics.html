Azure Basics

This page consolidates how the course project uses Azure App Service, Azure Static Web Apps, and Azure MySQL so support staff can verify each service configuration quickly.

WVU policy reminder: For course projects, request Azure resource groups through Statler ITS instead of creating them directly.

Azure Service Roles in This Project

Each Azure service has a specific responsibility. Keeping these responsibilities separate makes it easier to locate issues quickly when a deployment partially works.

Azure Service Purpose Typical Ownership
Resource Group Container for all class-team cloud resources Provisioned through Statler ITS
Static Web App (SWA) Hosts the built React frontend, uploaded by GitHub Actions Instructor-provisioned, team-configured
App Service (Linux, Node 24 LTS) Runs the Node.js backend API Instructor-provisioned, team-configured
Azure Database for MySQL Flexible Server Stores users Provisioned in Sprint 2, reused in deployment

MySQL Networking and TLS

The backend connects to Azure MySQL over TLS and verifies the server's certificate. Two network paths must be open: from each developer's computer (local development) and from the App Service (production).

  1. In Azure Portal, open the MySQL Flexible Server's Networking page.
  2. Add a firewall rule for each developer's public IP address (needed for local development and the mysql CLI).
  3. Enable Allow public access from any Azure service within Azure to this server, so the App Service can connect.
  4. The CA certificate (Download SSL Certificate on the same page) is committed at backend/config/DigiCertGlobalRootG2.crt.pem; it is public, not a secret.

How backend/config/database.js uses it:

const caCert = fs.readFileSync(new URL('./DigiCertGlobalRootG2.crt.pem', import.meta.url));

const pool = mysql.createPool({
  host: process.env.DB_HOST,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  port: Number(process.env.DB_PORT) || 3306,
  ssl: { ca: caCert, rejectUnauthorized: true },
});

App Service Environment Variables

In App Service go to Settings > Environment variables > App settings and verify:

Setting Expected value
DB_HOST <server>.mysql.database.azure.com
DB_USER Project database user
DB_PASSWORD Project database password (exactly this name)
DB_NAME Project database name (authdb in the reference app)
DB_PORT 3306 (optional)
FRONTEND_URL https://<your-swa>.azurestaticapps.net, exactly, no trailing slash
JWT_SECRET Long random secret value, different from any local one
NODE_ENV production

Click Apply; the app restarts. Do not add PORT: App Service sets it.

Why NODE_ENV=production matters: the frontend (*.azurestaticapps.net) and backend (*.azurewebsites.net) are different sites. In production the backend sets the login cookie as HttpOnly; Secure; SameSite=None; Partitioned, the only form browsers send on cross-site requests. Without it, login returns 200 but users are immediately treated as logged out.

App Service Runtime and Health

App Service controls runtime networking. The Node app must respect Azure runtime values instead of local defaults to boot correctly in production.

  • Runtime stack: Node 24 LTS on Linux. App Service starts the app with npm start.
  • The backend listens on the Azure-assigned port: const PORT = Number(process.env.PORT) || 5175;
  • Publish-profile deployments need Settings → Configuration → General settings → SCM Basic Auth Publishing Credentials turned on; otherwise Download publish profile is greyed out.
  • Validate after deploy: https://<backend>.azurewebsites.net/health returns {"ok":true,"env":"production"}.
  • Use Monitoring → Log stream for startup and database errors. A missing setting is reported as Missing required environment variables: ….
  • The backend calls Microsoft Planetary Computer (planetarycomputer.microsoft.com and *.blob.core.windows.net); outbound internet access is allowed by default.

Static Web App Deployment Basics

A Vite build copies environment values into the JavaScript bundle, so the backend URL must be available in GitHub Actions when the frontend is built, not later.

  • When creating an SWA, the deployment source decides who writes the workflow: GitHub makes Azure commit a workflow to the chosen repo (student option A); Other lets you deploy with your own workflow and the SWA's deployment token (the reference repo).
  • Build output is dist for Vite projects.
  • Provide the backend URL through the secret VITE_BACKEND_API_URL.
  • frontend/public/staticwebapp.config.json (a navigationFallback to /index.html) makes refreshes on /map and /login work.
  • Confirm the deployed frontend sends requests to https://<appservice>.azurewebsites.net/auth/...; the browser console also prints Frontend API Base URL: ….

Operational Checklist for Staff

  • Resource group exists and is mapped to the correct course team.
  • App Service runs Node 24 LTS, starts, and returns a successful health check.
  • SWA deployment is green in GitHub Actions.
  • FRONTEND_URL matches the SWA URL exactly, and NODE_ENV is production.
  • Backend connects to MySQL without timeout or TLS errors.
