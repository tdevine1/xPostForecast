Let your app talk to the rest of the internet

So far your app only knows what is in your own database. In Sprint 3 it asks another service for information, such as weather, earthquakes, books, or sports scores, and shows the answer to your users. Programs ask each other for data through an API. This guide explains what that means from scratch, then walks you through connecting your own project to one.

Before you start: you need the Sprint 1 frontend and the Sprint 2 backend working on your computer (login included). You do not need any Azure knowledge yet. New words are explained in the Glossary.
The xPostForecast repository is an example, not a template. It shows one finished way to do this with one API. Pick your own API for your own topic, and use the Sprint 3 branch to see how a finished version is organised.

1. What you are building

By the end of Sprint 3 your project does this:

  Browser (React)  --1. user clicks a button-->  Your backend (Express)
                                                    |
                         2. checks the user is logged in
                         3. asks the outside API for data
                                                    v
                                              Outside API
                                                    |
                         4. reads the answer, tidies it up
                                                    |
  Browser (React)  <--5. sends back clean JSON------+
        |
  6. shows it (a map, a table, a chart...)

Notice that the browser never talks to the outside API directly. Your backend does. Section 9 explains why that is the usual, safer design. The reference app follows exactly this shape: the browser asks your backend for /temperature/2020-07-01, and the backend asks Microsoft's Planetary Computer for weather data.

2. What an API is

API stands for application programming interface. Think of a restaurant. You don't walk into the kitchen. You read a menu (what you may ask for), tell the waiter your order in a set format, and the kitchen sends back a dish. A web API is the same:

RestaurantWeb API
The menuThe API's documentation: what you can ask for and how.
Placing an orderSending a request to a web address (a URL).
A particular dish on the menuAn endpoint: one URL that does one job, such as /forecast.
The dish arrivingThe response: data, usually written in JSON (section 4).
"Sorry, we're out of that"An error status code, such as 404 (section 3).

You have already built an API: the Sprint 2 backend answers /auth/login and /auth/register, and your frontend calls them. In Sprint 3 you also become a client of someone else's API. The same ideas apply in both directions.

3. HTTP in five minutes

Web APIs speak HTTP, the same language your browser uses to load pages. Every exchange is a request followed by a response.

A request has four parts

PartWhat it isExample
MethodThe kind of actionGET (read), POST (create or send data), PUT/PATCH (change), DELETE (remove)
URLWhere to send it, plus optional query parameters after a ?https://api.open-meteo.com/v1/forecast?latitude=39.63&longitude=-79.96
HeadersExtra information about the requestContent-Type: application/json says "my body is JSON"; Authorization: Bearer ... carries a key
BodyData you send (mostly with POST){"username":"alice","password":"..."}

Query parameters are name=value pairs joined by &. Characters like spaces and & must be encoded, which is why code uses encodeURIComponent() or URLSearchParams instead of gluing strings together.

A response has a status, headers, and a body

The status code is a three-digit number saying how it went. Learn the groups:

CodeMeaningCommon ones
2xxIt worked200 OK, 201 Created
3xxLook somewhere else301/302 redirects
4xxYour request was wrong400 bad input, 401 not logged in or bad key, 403 not allowed, 404 not found, 429 too many requests
5xxThe server had a problem500 server error, 502 a server it depends on failed, 503 unavailable

A useful rule: 4xx means "fix your request", 5xx means "not your fault, try again later". The reference backend uses 502 Bad Gateway when the outside weather service fails, so the frontend can tell "you typed a bad date" (400) from "their server is down" (502).

4. JSON

JSON (JavaScript Object Notation) is the text format most web APIs use to send data. It looks like JavaScript objects and arrays, which makes it easy to use in your code. Here is a real answer from the free Open-Meteo weather API: 

{
  "latitude": 39.641438,
  "longitude": -79.95688,
  "timezone": "GMT",
  "elevation": 243.0,
  "current_units": { "time": "iso8601", "temperature_2m": "°F" },
  "current": { "time": "2026-11-17T04:30", "interval": 900, "temperature_2m": 38.6 }
}

JSON has only six kinds of value:

KindExampleNotes
Object{ "name": "Ada", "age": 36 }Named values in { }. Names must be in double quotes.
Array[1, 2, 3]An ordered list in [ ]. Often a list of objects, such as 9,700 temperature points.
String"hello"Double quotes only.
Number38.6No quotes. Dates are not a type: they travel as strings like "2026-11-17T04:30".
Booleantrue, falseLowercase, no quotes.
Nullnull"No value".

Using JSON in JavaScript

const text = '{"current":{"temperature_2m":38.6}}';  // JSON is just text
const data = JSON.parse(text);                       // text -> JavaScript object
console.log(data.current.temperature_2m);            // 38.6
console.log(JSON.stringify(data));                   // object -> text again

// Arrays of objects are everywhere:
const points = [{ lat: 38.9, lon: -80.2, tavg: 54.1 }, { lat: 39.0, lon: -80.2, tavg: 55.3 }];
const warm = points.filter((p) => p.tavg > 55);   // [{ lat: 39.0, ... }]

With fetch, await res.json() does the JSON.parse for you. With axios, response.data is already parsed. Two things trip people up:

  • Reading something that isn't there. data.current.temperature_2m throws if current is missing. Use optional chaining, data.current?.temperature_2m, and check the shape before you trust it (section 11).
  • Not everything is JSON. Some APIs return CSV, XML, images, or binary files. The reference app's data file is a GeoTIFF (binary), which it downloads and decodes with a library. Check the Content-Type response header.

Tip: paste JSON into a formatter, such as the one built into your browser's dev tools or VS Code (Format Document), to read it comfortably.

5. REST, and other styles

REST is a popular way to design a web API. A REST API is organised around resources (things, like users or books), each with its own URL. The HTTP method says what to do with it.

You want to…Method and URLTypical status
List all booksGET /books200
Read one bookGET /books/42200, or 404 if there is no book 42
Add a bookPOST /books with a JSON body201 Created
Change a bookPUT /books/42 or PATCH /books/42200
Delete a bookDELETE /books/42200 or 204

Habits of a good REST API (and of the ones you write):

  • URLs are nouns, methods are verbs. GET /books, not /getAllBooks.
  • Stateless. Each request carries everything the server needs (such as the login cookie or key). The server doesn't remember the last request.
  • GET never changes anything, so it is safe to repeat and to cache.
  • Honest status codes and JSON error bodies, like { "error": "Date must be YYYY-MM-DD" }.

Not every API is REST. You will meet these names, so here is what they mean in one line each:

StyleOne-line ideaGood for
RESTMany URLs, one per resource; methods say the action.Most public data APIs. What you will use.
GraphQLOne URL; you send a query that names exactly the fields you want.Apps that need different slices of data (GitHub offers one).
WebSockets / Server-Sent EventsA connection that stays open so the server can push updates.Live data: chat, prices, scores.
SOAPOlder, XML-based, very formal.Some banks and government systems.
gRPCCompact binary messages between servers.Services talking to each other inside a company.
Files and feedsYou download a file (CSV, GeoJSON, GeoTIFF) from a URL.Large datasets, like the temperature grids in the reference app.

For this course, choose a REST API that returns JSON unless your instructor approves something else. Whatever the style, the skills are the same: read the docs, build a request, check the status, and handle the data.

6. Keys, limits, and paging

Most APIs have rules about who may call and how often. Learn to spot these in the documentation before you choose one.

TopicWhat it meansWhat you do
No authenticationAnyone may call it.Just send the request. (Open-Meteo and the reference app's data service work this way.)
API keyA long secret string that identifies you. Sent in a header or a query parameter.Create a free account, copy the key, put it in your backend's .env file as WEATHER_API_KEY=..., and read it with process.env.WEATHER_API_KEY. Never in the frontend, never committed.
Token / OAuthLog in as a user, get a short-lived token, send it as Authorization: Bearer <token>.Follow the provider's guide. Harder; avoid unless your topic needs it.
Rate limitA cap on requests per minute or day. Going over gives 429 Too Many Requests.Read the limit, cache answers you reuse, and don't call in a loop. Many APIs report your usage in headers such as X-RateLimit-Remaining.
PaginationA long list comes in pages (for example 20 at a time) with a link or number for the next page.Request the page you need (?page=2&limit=20), or loop carefully until there are no more.
Terms of useRules about what you may do with the data.Read them. Many require credit (attribution) or a User-Agent header that names your app.
An API key is a password. Anyone who has it can use your quota and may get your account blocked. Keep it in .env (which .gitignore excludes), in a GitHub secret for deployment, and out of chat messages and AI tools. If a key leaks, revoke it at the provider and make a new one.

7. Choose your API

Pick the API after you pick your topic, and check it against this list before you commit:

  • It has documentation with example requests and responses.
  • It is free at the level you need, and the limits are enough for a class project.
  • It returns JSON (or another format you can handle).
  • Its terms of use allow a student project, and you know what credit it needs.
  • You can make a request in your browser or curl and get a sensible answer (section 8).
  • The data is interesting enough for several screens: a list, a detail view, a chart or map. A single number is too small.
  • Your teammates all understand it. Choose one and write down why.

Places to look. Free tiers and terms change, so confirm on the provider's own site:

TopicExamples to explore
Weather and climateOpen-Meteo, the U.S. National Weather Service API (api.weather.gov), NOAA data services
Space and scienceNASA Open APIs (api.nasa.gov), USGS earthquake feeds
Government and public dataData.gov catalog, U.S. Census Bureau API
Software and developersGitHub REST API
Games, books, movies, fun dataPokéAPI, Open Library
Browsing many optionsThe community-maintained "public-apis" list on GitHub

Ask your instructor to approve your choice before you build on it.

8. Try it before you code

Never write code against an API you haven't called by hand. Doing it by hand shows you the real answer, and then your code has something to match.

  1. Open the documentation and find one endpoint that gives what you need. Note its URL, its parameters (which are required?), and an example response.
  2. Call it in the browser if it is a GET with no key: paste the URL into the address bar. For Open-Meteo: https://api.open-meteo.com/v1/forecast?latitude=39.63&longitude=-79.96&current=temperature_2m&temperature_unit=fahrenheit
  3. Call it from a terminal with curl, which also shows headers and works for POST. The -i flag prints the status line and headers: 
    curl -i "https://api.open-meteo.com/v1/forecast?latitude=39.63&longitude=-79.96&current=temperature_2m"

# A POST with a JSON body (this is the kind of call the reference app makes)
curl -X POST https://planetarycomputer.microsoft.com/api/stac/v1/search \
  -H "Content-Type: application/json" \
  --data '{"collections":["noaa-nclimgrid-monthly"],"datetime":"2020-07-15T00:00:00Z","limit":1}'
  4. Break it on purpose. Send a latitude of 999. The API answers 400 Bad Request with a JSON body like {"error":true,"reason":"Latitude must be in range of -90 to 90°..."}. Now you know what errors look like before you handle them.
  5. Write down the request and a trimmed example response in your team's notes. You will copy it into your tests (section 12).

9. Call it from your backend

Why not call the API from React?

  • Secrets. Code in the browser is visible to everyone. An API key placed there is public.
  • CORS. Browsers block a page from reading another site's answer unless that site allows it. Your own backend isn't a browser, so it has no such restriction.
  • Control. Your backend can require login, cache answers, tidy the data into just what your screens need, and hide the outside API's quirks. If you switch APIs later, the frontend doesn't change.

The shape of a good route

Every Sprint 3 route follows the same five steps. The reference app's routes/stac.js is a full example:

  1. Check the input from your own user. Reject bad input with 400 before doing any work.
  2. Check the cache. If you already have the answer, return it. This saves quota and time.
  3. Call the outside API with a timeout, and check res.ok.
  4. Read and check the answer. Pull out only the fields you need, and convert units or names to what your frontend expects.
  5. Map failures to honest status codes: your user's mistake is 4xx; the outside API failing is 502; "no data for that" is 404.

A small, complete example

This route returns the current temperature for a point, using Open-Meteo. Adapt the shape, not the details:

// routes/weather.js
import express from 'express';
const router = express.Router();

const cache = new Map();                // 'lat,lon' -> { value, savedAt }
const CACHE_MS = 10 * 60 * 1000;        // reuse an answer for 10 minutes

router.get('/current', async (req, res) => {
  // 1. Check the input
  const lat = Number(req.query.lat);
  const lon = Number(req.query.lon);
  if (!Number.isFinite(lat) || !Number.isFinite(lon) || Math.abs(lat) > 90 || Math.abs(lon) > 180) {
    return res.status(400).json({ error: 'lat and lon must be numbers in range' });
  }

  // 2. Check the cache
  const key = `${lat},${lon}`;
  const hit = cache.get(key);
  if (hit && Date.now() - hit.savedAt < CACHE_MS) return res.json(hit.value);

  try {
    // 3. Call the outside API (build the URL safely, set a timeout)
    const url = new URL('https://api.open-meteo.com/v1/forecast');
    url.search = new URLSearchParams({
      latitude: lat, longitude: lon, current: 'temperature_2m', temperature_unit: 'fahrenheit',
    });
    const upstream = await fetch(url, { signal: AbortSignal.timeout(8000) });
    if (!upstream.ok) throw new Error(`Weather service answered ${upstream.status}`);

    // 4. Read and check the answer, keep only what the frontend needs
    const data = await upstream.json();
    const temp = data.current?.temperature_2m;
    if (typeof temp !== 'number') throw new Error('Unexpected response shape');
    const value = { lat, lon, tempF: temp, asOf: data.current.time };

    cache.set(key, { value, savedAt: Date.now() });
    return res.json(value);
  } catch (error) {
    // 5. Our user did nothing wrong: the outside service failed
    console.error('Weather lookup failed:', error.message);
    return res.status(502).json({ error: 'The weather service is unavailable. Try again later.' });
  }
});

export default router;

Then mount it behind your login check in app.js, exactly as Sprint 3 does for temperatures:

app.use('/weather', authMiddleware, weatherRoutes);   // logged-in users only

Why behind login? An open route lets anyone on the internet spend your API quota. Requiring a login means only your users can.

Node's built-in fetch (Node 24) needs no package. It only throws when the network fails, not when the server answers with an error status, so always check res.ok. (axios, by contrast, throws on any non-2xx status.)

What the reference app does that is more advanced

  • It makes a POST with a JSON body to a "search" endpoint, then follows a link in the answer to a second step (signing a file URL), then downloads a binary file and decodes it. Your API may be much simpler.
  • It picks fields by name (item.assets.tavg) because the order of keys in JSON is never guaranteed.
  • It caches by month (the data never changes) and caps the answer size as a safety limit.

Read it in routes/stac.js after you have written your own.

10. Show it in your frontend

The browser now only ever talks to your backend, using the shared client from Sprint 2:

// src/api.js: one axios instance for every call
const api = axios.create({
  baseURL: import.meta.env.VITE_BACKEND_API_URL,
  withCredentials: true,       // send the login cookie
});

A page that loads data needs to handle four states, not one. Beginners often build only the happy path:

StateWhat the user sees
Nothing asked yetInstructions, or an empty screen that makes sense.
LoadingA spinner. The first call can take seconds.
SuccessThe data.
ErrorA clear message that says what to do next, and the old data cleared so it isn't mistaken for new data.
 
const [data, setData] = useState(null);
const [isLoading, setIsLoading] = useState(false);
const [error, setError] = useState('');

const load = async () => {
  setError('');
  setIsLoading(true);
  try {
    const { data } = await api.get('/weather/current', { params: { lat: 39.63, lon: -79.96 } });
    setData(data);
  } catch (err) {
    if (err.response?.status === 401) { /* session expired: send the user to /login */ return; }
    setData(null);
    setError(err.response?.data?.error ?? 'Could not reach the server. Is the backend running?');
  } finally {
    setIsLoading(false);        // runs on success AND failure
  }
};

Use the backend's own error message when it sends one. That is why the backend returns JSON errors with plain-English text. Compare with the reference app's MapPage.jsx.

11. Keep it safe

Data from another service is untrusted input, just like text typed into a form. The reference app learned this the hard way: SonarQube Cloud flagged it for downloading a file from an address that came out of another service's JSON, a weakness called server-side request forgery. If that answer were ever tampered with, the server could be tricked into requesting internal addresses. The fix was a short check before the download: 

export function assertTrustedAssetUrl(href) {
  const url = new URL(href);                      // throws if it isn't a URL at all
  if (url.protocol !== 'https:' || !url.hostname.endsWith('.blob.core.windows.net')) {
    throw new Error(`Refusing to request an untrusted host: ${url.hostname}`);
  }
  return url.href;
}

Habits that apply to any API:

  • Check the shape of an answer before using it (typeof temp === 'number', Array.isArray(items)).
  • Only follow web addresses you expect. If an answer gives you a URL to fetch, check its host first.
  • Build URLs with URL and URLSearchParams, never by pasting user text into a string.
  • Set a timeout (AbortSignal.timeout(8000)) so a slow API can't hang your route forever.
  • Keep keys on the server and out of logs. Log error messages, not whole requests with headers.
  • Don't send the outside API's raw error text to your users. It may reveal internals. Log it, and send a plain message.
  • Respect rate limits with caching, and give credit as the terms require.

12. Test without the network

Tests must not depend on someone else's server being up, fast, or free. Replace fetch with a fake that returns the example response you saved in section 8. Vitest makes this easy: 

import { afterEach, describe, expect, it, vi } from 'vitest';
import request from 'supertest';
import app from '../app.js';

afterEach(() => vi.unstubAllGlobals());

describe('GET /weather/current', () => {
  it('returns the temperature in °F', async () => {
    vi.stubGlobal('fetch', vi.fn(async () =>
      Response.json({ current: { time: '2026-11-17T04:30', temperature_2m: 38.6 } })));

    const res = await request(app).get('/weather/current?lat=39.63&lon=-79.96').set('Cookie', loginCookie());

    expect(res.status).toBe(200);
    expect(res.body.tempF).toBe(38.6);
  });

  it('answers 502 when the outside service fails', async () => {
    vi.spyOn(console, 'error').mockImplementation(() => {});
    vi.stubGlobal('fetch', vi.fn(async () => new Response('busy', { status: 503 })));

    const res = await request(app).get('/weather/current?lat=39.63&lon=-79.96').set('Cookie', loginCookie());

    expect(res.status).toBe(502);
  });

  it('rejects a latitude that is out of range, without calling the API', async () => {
    const fetchSpy = vi.fn();
    vi.stubGlobal('fetch', fetchSpy);

    const res = await request(app).get('/weather/current?lat=999&lon=0').set('Cookie', loginCookie());

    expect(res.status).toBe(400);
    expect(fetchSpy).not.toHaveBeenCalled();
  });
});

(loginCookie() is a small helper that signs a token with your test JWT_SECRET; see the reference app's temperature.test.js.) Test each status your route can return: success, bad input, no data, and outside failure. Those tests also raise your coverage for Milestone 6.

13. When something breaks

Work from the outside in: can you call the API by hand? Then does your backend route work in curl? Only then look at React.

What you seeLikely causeWhat to do
401 or 403 from the outside APIMissing, wrong, or expired keyCheck the key's name in .env, restart the backend, and check where the docs say to send it (header or query).
404 from the outside APIWrong path, or nothing exists for that inputCompare your URL with the docs, character by character.
429Rate limit reachedSlow down and cache. Wait for the limit to reset.
SyntaxError: Unexpected token < in JSONThe "JSON" was really an HTML error pageLog await res.text() and the status to see what came back.
Cannot read properties of undefinedThe answer doesn't have the shape you assumedLog the answer, check the docs, and use ?. plus a shape check.
Your route answers 401Not logged in, or the cookie wasn't sentLog in first; in curl use -b cookies.txt; in React use the shared api client.
Browser console: CORS errorThe browser is calling the outside API directly, or FRONTEND_URL is wrongCall your own backend instead (section 9), and check FRONTEND_URL.
Works for you, empty for othersA secret or setting exists only on your computerList every .env variable your code reads, and make sure each is set wherever the code runs.
The first request is slow, later ones fastThe outside call is slow, and your cache worksThat is normal. Show a loading spinner.

Still stuck? Copy the exact error and the request you sent (without keys), say what you tried, and ask your team, then your instructor. The AI guide shows how to use an AI tool to understand an error without pasting secrets.

14. Checklist

  • Your API is chosen, approved, and its terms are read.
  • You called it by hand (browser or curl) and saved an example request and response.
  • Any API key is in .env and a GitHub secret, never in code or chat.
  • Your backend route validates input, caches, sets a timeout, checks res.ok, and checks the shape of the answer.
  • Failures map to honest status codes (400, 404, 502) with JSON error messages.
  • The route sits behind your login check.
  • The frontend handles empty, loading, success, and error states, and calls only your own backend.
  • Tests cover success and each failure without using the network.
  • Your README says which API you use, where to get a key, and how to set it up.
