AI-savvy and well educated

The developers employers want next use AI tools every day, and they can also read, debug, test, and explain every line they ship. AI makes writing code faster. It doesn't decide whether the code is right, secure, or what your team needs. That judgment is the job, and it's what this course teaches.

This guide shows how to get both: the speed of AI and the skills that let you trust what it gives you.

Course rules come first. CS 330 allows AI tools in lecture activities and the course project, with conditions (see section 10). If the syllabus and this guide ever disagree, the syllabus wins.

1. The mindset

Treat AI like a knowledgeable teammate who is fast, confident, and sometimes wrong. You wouldn't merge a teammate's code without reading it, and you wouldn't let them take your exam. Hold AI to the same standard.

Do: use it as a tutor and a reviewer

  • Ask why an error happens, not only how to make it go away.
  • Have it break down unfamiliar code line by line.
  • Ask it to quiz you on a concept before you build with it.
  • Ask it to review code you wrote for bugs and security problems.

Don't: use it as a copy-paste machine

  • Pasting multi-file solutions you haven't read.
  • Committing code you haven't run locally.
  • Asking it to do the assignment instead of helping you learn it.
  • Pasting secrets or private data into a chat (see section 3).
The Explain It Back rule: before you commit code an AI wrote or fixed, explain every line to a teammate without looking at the chat. If you can't, ask: "Explain lines 5 to 12 in plain English, and tell me what would break if I removed each one." You own everything you commit, including its bugs.

2. Learning mode and building mode

How you use AI should depend on whether you already understand what you're building.

Learning mode: the topic is new to you

Examples: your first Express route, your first JWT, your first SQL join.

  • Ask for explanations, analogies, hints, and quizzes.
  • Write the code yourself, even if it's slower.
  • Ask the AI to review your attempt instead of writing its own.

Building mode: you understand it already

Examples: your fifth route, a form like the one you built last week, test cases.

  • Let AI draft code, tests, and repetitive setup.
  • Review the draft as carefully as a teammate's pull request.
  • Run it, test it, and make sure you can explain it.

Rule of thumb: if you couldn't write a rough version yourself, you're in learning mode. Skipping learning mode feels faster now and costs you later, in debugging, in code review, and in interviews.

3. Never paste secrets

Anything you paste into an AI chat leaves your computer. Depending on the tool and its settings, it can be stored, reviewed, or used for training. Treat a chat box like a public forum.

Never paste or upload:
  • the contents of any .env file;
  • DB_PASSWORD, JWT_SECRET, API keys, or connection strings;
  • Azure publish profiles or Static Web Apps deployment tokens;
  • screenshots of the Azure Portal, a terminal, or VS Code that show any of the above;
  • teammates' or users' personal information.

Before you paste a stack trace or a file, read it and replace anything secret with a placeholder like <DB_PASSWORD>. The AI doesn't need real values to help you.

AI tools inside your editor can read the files you have open and, in agent mode, other files in your project. Close .env before you chat, and read every command an agent wants to run before you allow it.

This has happened in this course. The reference app's own repository once exposed a database password through a committed editor settings file. If a secret ever ends up in a chat or a commit, treat it as public: change it in Azure first, then tell your team.

4. Check before you trust

AI tools learned from years of older code, so they often suggest patterns this project doesn't use. When a suggestion doesn't match the course stack, the suggestion is usually what's out of date.

Before you use a suggestion:

  • Check that every package exists. Look it up on npmjs.com: it should have a real repository, recent releases, and many weekly downloads. AI sometimes invents package names, and attackers publish malware under names like those.
  • Check the version. Ask: "Which version of this library does your answer assume?" Compare it with package.json.
  • Check the official docs for anything about security, authentication, or deployment.
  • Run it. Code that looks right isn't tested code. Try it locally, including the error cases.

5. Prompts that teach

Good prompts give context and ask for understanding. Include the stack, what you expected, what happened, the exact error, and what you've already tried. These examples come from problems CS 330 teams hit every semester.

Frontend · React

State vs. props

Not sure where data should live, or how to pass it between components?

"Explain the difference between React state and props using an analogy of a house and its rooms. Then ask me two questions to check I understood."

Backend · Express

Middleware and routes

Confused about what happens between a request arriving and your handler running?

"Walk me step by step through how a POST to /auth/login passes through cors(), express.json(), and cookieParser() before it reaches my route handler in Express 5."

Networking · CORS

"Blocked by CORS policy"

Your React app can't reach your backend?

"My React app on localhost:5173 gets 'blocked by CORS policy' when it calls my Express backend on localhost:5175 with credentials. Explain what the browser is checking and which settings on each side must match. Don't give me the code yet."

Security · Auth

JWTs in cookies

Not sure how the backend knows you're logged in?

"How does an HTTP-only cookie holding a JWT prove a user is logged in? Walk through login, a page refresh, and logout, and tell me what an attacker could and couldn't do if they stole the cookie."

Database · MySQL

Safe queries

Writing your first query that uses user input?

"Explain why ? placeholders in mysql2 prevent SQL injection. Show me an injection that would work against a query built by joining strings, and explain why it fails with placeholders."

Deployment · Azure

Works locally, breaks in the cloud

Login works on localhost but not after deploying?

"Why would a login cookie that works on localhost stop working when my frontend is on azurestaticapps.net and my backend is on azurewebsites.net? Explain SameSite and Secure before suggesting a fix."

7. AI in VS Code

Get GitHub Copilot

Verified students can use GitHub Copilot at no cost through GitHub Education. After your student status is approved, install the GitHub Copilot extension in VS Code and sign in with the same GitHub account.

Ask about the code in front of you

  • Open the chat with Ctrl+Alt+I (Ctrl+Cmd+I on macOS).
  • Select confusing code and type /explain in the chat to get a walkthrough.
  • Write a comment saying what you think a block does, then ask Copilot whether you're right.

Use agent mode carefully

  • Commit first, so you can undo everything with one click if the changes go wrong.
  • Ask for one small change at a time, and read every changed file before you keep it.
  • Read each terminal command before you allow it to run.

Turn off autocomplete while you learn

Inline suggestions finish your thought before you've had it. When you're in learning mode, use the Copilot menu in the status bar to turn off inline suggestions, and turn them back on when you're building.

Give Copilot your team's rules

Copilot reads a file named .github/copilot-instructions.md in your repository and follows it in every chat. Your team can use it to keep Copilot in tutor mode: 

This is a CS 330 student project: React 19 + Vite frontend, Express 5 backend
on Node 24 (ES modules), MySQL on Azure through mysql2, and login with a JWT in
an HTTP-only cookie.

- Explain the concept before showing code, and keep code examples short.
- When I share an error, help me find the cause instead of rewriting my file.
- Point out anything that depends on a specific library version.
- Never ask me for passwords, keys, tokens, or the contents of .env files.

Share errors the right way

When Express or Node crashes, copy the whole error from the terminal, including the stack trace and line numbers, plus the code it points to. Read it for secrets first (section 3).

8. AI on a team

  • You can explain what you open a pull request for. Every line, whether you or an AI typed it.
  • Reviewers ask. "Walk me through this function" is a normal, friendly review question.
  • Say when AI wrote a significant part. A line in the pull request description is enough, for example: "Copilot drafted the tests; I checked and edited them."
  • Agree as a team on which tools you use and how, so nobody is surprised in code review.
  • Report your contribution honestly on each milestone's contribution allocation sheet.

9. Keep your skills sharp

Technical interviews, production outages, and this course's exams (open notes, but no electronic sources) all happen without an AI assistant. Make sure you can do these on your own:

  • read a stack trace and find the line that failed;
  • use the browser's developer tools (Console and Network tabs) to see what a request sent and got back;
  • write a simple SQL query, route, and React component from memory;
  • explain how CORS, cookies, and JWT login work in this project;
  • resolve a Git merge conflict.

A good habit: once a week, solve one small problem without AI, then ask an AI to review your solution. You'll see how much you've learned, and what to practice next.

10. Course AI policy

The CS 330 syllabus treats AI tools (large language models and code assistants) as part of normal software engineering practice. You may use them in lecture-related activities and in the course project. This is a summary; the syllabus on eCampus is the official version.

When you use AI, you're expected to

  • use it as a support tool, not a replacement for understanding;
  • review, verify, and validate anything it produces before you use it;
  • modify and improve AI-generated code rather than submitting it verbatim;
  • follow any documentation or citation requirements for the project;
  • be prepared to explain and defend all of your submitted work.

AI can help you with

  • brainstorming design or architecture options;
  • generating or refining code that you understand;
  • debugging and interpreting error messages;
  • writing documentation drafts;
  • deployment and configuration tasks.
All submitted work must reflect your own understanding. Not being able to explain code or a design decision you submitted may be treated as a violation of course expectations, whether or not you used AI.
  • Quizzes are completed individually, without help from your peers.
  • Exams are open notes, but no electronic sources are allowed, so no AI tools.
  • You may be invited to join a voluntary, WVU-approved research study on how AI tools affect learning in software engineering. Taking part, or not, doesn't affect your grade.

If anything here is unclear for a particular assignment, ask your instructor before you start.
