Let a tool review every push

SonarQube Cloud reads your code and your test results on every push and reports bugs, security problems, maintainability issues, duplicated code, and how much of your code your tests actually run. This guide connects it to your team's GitHub repository and your existing GitHub Actions workflow.

The reference app already does this: see sonar-project.properties and the sonar job in .github/workflows/ci.yml on the main branch. You build the equivalent in your own repository.

Scope: this guide covers the SonarQube part of Milestone 6. Your assignment instructions decide what else is required (unit testing documents, Selenium, the testing report). If they and this guide ever disagree, the assignment wins.

Words you will see

  • SonarQube Cloud: a website that reads your code and reports problems, free for small projects.
  • Static analysis: reading code without running it to spot bugs, security risks, and messy code.
  • Test coverage: what percentage of your code your tests actually ran. Untested code is where bugs hide.
  • Token: a long random string that proves who you are to a service, like a password you can revoke. Never share or commit one.
  • Secret: GitHub's hidden storage for a token, so a workflow can use it without it appearing in your code.
  • Workflow: the written instructions GitHub follows after each push. Never written one? See Writing GitHub workflows first.

More definitions are in the Glossary.

1. What you get

  • Reliability: likely bugs, such as a promise that is never awaited.
  • Security: vulnerabilities, plus security hotspots: code that is only a problem depending on how it is used, so a person has to review it.
  • Maintainability: "code smells" such as overly complex functions or unused code.
  • Coverage: the share of your code that your automated tests run, file by file.
  • Duplications: copy-pasted blocks.
  • Quality Gate: a pass/fail verdict on the code you changed recently. The default gate ("Sonar way") looks at new code only: coverage, duplication, and the ratings above.

It is static analysis: it reads your code without running it. It finds a different class of problems than your Vitest tests (which check behavior) or Selenium (which drives a real browser), so it complements them rather than replacing either.

2. Before you start

  • Your team's repository lives in your group's GitHub organization, and every teammate has been added (see Sprint 1).
  • npm test passes in frontend/ and backend/, and your CI workflow is green.
  • You use Node 24 locally (node -v). Older versions fail with "Cannot find native binding" (see troubleshooting).
  • You know who your repository Admin is.
Who does what (least privilege): the steps in sections 4 to 6 need organization-owner or repository-Admin rights, so one person does them. Everyone else just pushes code with Write access and reads the results. Don't make teammates Admins to "help".

3. Free plan limits

SonarQube Cloud's Free plan is enough for this project, with a few limits to know about:

  • Private repositories: up to 50,000 lines of code per SonarQube organization. The reference app is roughly 1,100 lines of source, so you have plenty of room. Because each group has its own organization, you don't share this limit with other groups.
  • Members: up to five per organization on the Free plan. If your team has more than five people, tell your instructor before you start.
  • Public repositories have no line limit.

Plans and limits change, so check the current subscription plans page if something here doesn't match what you see.

4. Connect your GitHub organization

Do this once per team. Menu names may differ slightly from the wording here; follow the on-screen prompts.

  1. Go to sonarcloud.io and choose Log in with GitHub.
  2. Choose Import an organization from GitHub and select your group's organization.
  3. GitHub asks you to install the SonarQube Cloud app on that organization. Only an organization owner can approve this. Choose Only select repositories and pick your team's repository, rather than giving the app access to everything.
  4. Choose the Free plan and create the organization. Note the organization key shown for it; you'll need it in section 7.
  5. Invite your teammates to the SonarQube Cloud organization so they can see the results (remember the five-member limit).

5. Create the project

  1. In SonarQube Cloud choose Analyze new project and select your team's repository.
  2. When it asks how to analyze, choose With GitHub Actions. The page shows a snippet; you'll use a version of it in section 7.
  3. Open the project's Information page and copy its project key (usually <organization>_<repository>).
  4. Under Administration → Analysis Method, make sure Automatic Analysis is turned off. Automatic Analysis can't read your test coverage reports, and running both causes an error.

6. Token and variable

Your workflow proves to SonarQube Cloud who it is with an access token, stored as a GitHub secret.

  1. In SonarQube Cloud click your profile picture (top right) → My Account, then open Access tokens (or go straight to sonarcloud.io/account/access-tokens). On the Personal Tokens tab type a Token name such as github-actions, and set Expires in to a date after your project is finished: the default is only 30 days, and the scan stops working the day the token expires. Click Generate Token and copy it right away; it is shown only once. SonarQube may suggest "Scoped Organization Tokens"; those need a paid plan, so use a personal token.
  2. In your GitHub repository go to Settings → Secrets and variables → Actions (visible to the repository Admin only).
  3. Secrets tab → New repository secret: name SONAR_TOKEN, value the token.
  4. Variables tab → New repository variable: name SONAR_ENABLED, value true. The workflow's sonar job only runs when this is set, so teams that haven't finished setup still get a green build.
A token works like a password. Never commit it, put it in a file, send it in a chat, or paste it into an AI tool (see Never paste secrets). If it leaks, click Revoke next to it on the same Access tokens page and generate a new one.

7. Add the files to your repository

Your repository should have frontend/ and backend/ side by side, as in Sprint 1. Each piece below has a working copy in the reference app to compare with.

a. Coverage reports

SonarQube can't measure coverage itself; it reads a report your test tool produces. In each of frontend/ and backend/, install the coverage plugin at the same version as your Vitest: 

npm ls vitest                              # note the version, for example 5.0.3
npm install --save-dev @vitest/coverage-v8@5.0.3

Add a script to that folder's package.json:

"test:coverage": "vitest run --coverage"

Then tell Vitest what to report on. In frontend/vite.config.js, inside the existing test block: 

coverage: {
  provider: 'v8',
  reporter: ['text', 'lcov'],
  include: ['src/**/*.{js,jsx}'],
  exclude: ['src/**/*.test.{js,jsx}', 'src/main.jsx'],
},

For the backend, create backend/vitest.config.js:

import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    environment: 'node',
    coverage: {
      provider: 'v8',
      reporter: ['text', 'lcov'],
      include: ['**/*.js'],
      exclude: ['tests/**', 'server.js', 'vitest.config.js', 'coverage/**'],
    },
  },
})

Run npm run test:coverage in each folder. You should see a coverage table, and a coverage/lcov.info file appear (it is already git-ignored by the repo's .gitignore).

b. sonar-project.properties

Create this file at the top level of the repository, using the organization key and project key from sections 4 and 5:

sonar.organization=your-organization-key
sonar.projectKey=your-organization-key_your-repository

sonar.sources=frontend/src,backend
sonar.tests=frontend/src,backend/tests
sonar.test.inclusions=**/*.test.js,**/*.test.jsx,backend/tests/**
sonar.exclusions=**/node_modules/**,**/coverage/**,**/dist/**,**/*.test.js,**/*.test.jsx,backend/tests/**

sonar.javascript.lcov.reportPaths=frontend/coverage/lcov.info,backend/coverage/lcov.info

Project keys and organization keys aren't secrets, so committing this file is fine. Never put the token in it.

c. The workflow job

Add a sonar job to your existing .github/workflows/ci.yml, alongside your test jobs. Each line follows the same ideas as the CI jobs in Writing GitHub workflows:

  sonar:
    if: ${{ vars.SONAR_ENABLED == 'true' }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0

      - uses: actions/setup-node@v7
        with:
          node-version: '24'

      - name: Frontend tests with coverage
        working-directory: frontend
        run: |
          npm ci
          npm run test:coverage

      - name: Backend tests with coverage
        working-directory: backend
        run: |
          npm ci
          npm run test:coverage

      - name: Make coverage paths relative to the repository root
        run: |
          sed -i 's#^SF:#SF:frontend/#' frontend/coverage/lcov.info
          sed -i 's#^SF:#SF:backend/#' backend/coverage/lcov.info

      - name: SonarQube Cloud scan
        uses: SonarSource/sonarqube-scan-action@v8.5.0
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
  • fetch-depth: 0 downloads the full Git history so SonarQube can tell which code is new.
  • The path step matters. Each coverage report lists files relative to its own folder (routes/auth.js), but SonarQube looks for them from the repository root (backend/routes/auth.js). Without the step, the scan succeeds but coverage shows 0%.
  • Check the scan action's page for the newest version number before you copy this.

8. Run it and read it

  1. Commit the files and push. Before you git add, run git status and confirm no .env file or token is listed.
  2. On GitHub open the Actions tab and watch the CI run. The sonar job should go green.
  3. Open your project in SonarQube Cloud. Start with these views:
    • Overview: the Quality Gate verdict and headline numbers. Look at both New Code (recent changes) and Overall Code (everything).
    • Issues: filter by Reliability, Security, or Maintainability. Click one to see the exact line and an explanation of why it matters and how to fix it.
    • Security Hotspots: each needs a person to mark it Safe or fix it.
    • Measures → Coverage: per-file coverage. Low-coverage files show where your tests have gaps.
    • Duplications: repeated code blocks.
  4. Pick one real issue and fix it. Push, wait for the next run, and confirm it disappears. This before-and-after is a good example for your report.

Once connected, SonarQube Cloud also reports the Quality Gate on your pull requests, so a reviewer can see it before merging.

Don't chase a perfect score. Read each finding before acting. Some are real bugs, some are style preferences, and some are false alarms. Deciding which is which, and writing down why, is the skill.

Example: a failed Quality Gate on the reference app

The first scan of xPostForecast failed the Quality Gate on New Code. A red gate on the first scan is normal. These were the three failed conditions and what the team did about each:

FindingWhat it meantWhat we did
Coverage 67.5% (needs 80% or more) Too many lines were never run by a test. The per-file view showed the gaps: the login and register pages, the map component, the database setup, and the error paths of the data route. Wrote tests for those files. Coverage went above 90% in both folders.
Reliability C: "Promises must be awaited…" Four places started an asynchronous action (such as navigate(...)) and ignored its result, so a failure there would vanish silently. Marked the deliberate ones with void, which says "I know this runs in the background".
Security C: "Server-side request forgery via unsanitized user input" The server downloads a file from a web address that came from another service's response. If that response were tampered with, our server could be tricked into requesting any address it can reach, such as internal ones. Added a check that only accepts https addresses on Azure Blob Storage, before asking to sign a URL and again before downloading. Added tests that prove other addresses are refused. SonarQube still listed the lines afterwards, because it cannot tell that a check like this makes the address safe. So we read each finding again, confirmed the check really covers it, and recorded the decision (see below).

The lesson for your own report: treat anything that comes from outside your code as untrusted (a form field, a URL parameter, or another website's response), and check it before you act on it. If SonarQube still flags a line after you added a proper check, read why: if you are sure it is a false alarm, mark the issue Accepted or False positive and write a sentence explaining your reasoning.

9. Use it in your testing report

Useful evidence to capture for your Milestone 6 report, with screenshots:

  • The Overview page showing the Quality Gate result and coverage from your first successful scan (Initial Results).
  • The Issues list for your first scan, and the same list after your fixes (Initial Results, Lessons Learned).
  • The per-file Coverage view, with a note on which components are least covered and why (Scope and limitations).
  • A short description of the workflow: it runs on every push and pull request, which is your automated regression check, and a failing run is how you find out a change broke something (Testing Strategy).

Remember what it can't do: it doesn't click through your app or check that features behave correctly. Say so in your limitations, and pair it with your unit tests and browser tests.

10. Troubleshooting

Symptom Likely cause Fix
The sonar job shows as skipped SONAR_ENABLED isn't set to true Add it as a repository variable (not a secret), section 6.
Scan fails with "Not authorized" or "project not found" Wrong or missing SONAR_TOKEN, or a typo in sonar.organization / sonar.projectKey Re-check the keys on the project's Information page; generate a new token and replace the secret.
The scan worked for a while, then fails with "Not authorized" The token expired (the default lifetime is 30 days) Generate a new token under My Account → Access tokens with a later expiry, and replace the SONAR_TOKEN secret.
Error mentioning Automatic Analysis, or "already analyzed" Automatic Analysis is still on Turn it off under Administration → Analysis Method.
Scan succeeds but coverage is 0% or missing The path-prefix step is missing, a report wasn't produced, or sonar.javascript.lcov.reportPaths is wrong Confirm npm run test:coverage creates coverage/lcov.info in both folders; keep the sed step; match the report paths in the properties file.
The coverage step fails with "Cannot find native binding" (locally or in CI) Node older than 24 Run node -v. Install Node 24 LTS, delete node_modules, and run npm ci again. CI must use node-version: '24'.
Analysis fails saying the organization reached its maximum lines Free plan private-code limit (50,000 lines) Exclude generated or vendored code in sonar.exclusions, or ask your instructor.
Quality Gate fails even though the build is green New code doesn't meet the gate, often coverage on new code Open the failed condition on the Overview page. Add tests for the new code or, for a justified exception, discuss it in your report.
