Teach GitHub to do the boring parts

Every time you push code, someone has to run the checks, build the site, and upload it to Azure. A workflow is a set of written instructions that makes GitHub do all of that for you, the same way every time. This guide builds three workflows from nothing, explains every line, and tells you what to do when one turns red.

Before you start: you need your own repository with frontend/ and backend/ folders side by side (Sprint 1), working npm test in both, and for the deploy workflows the Azure resources your instructor created (Sprint 4). New words are explained in the Glossary.
This repo is an example, not a template. The reference app's workflows are on GitHub. Read them, but type your own; you will learn far more, and your folder names and secrets will be yours.

1. What a workflow is

Picture a checklist taped to a robot: "when someone pushes code, download it, install the packages, run the tests, and tell me if anything fails." GitHub Actions is that robot, and a workflow file is the checklist.

WordPlain meaning
WorkflowOne checklist, saved as a file in .github/workflows/ (the folder name must be exact).
Trigger (on:)What starts it: a push, a pull request, or a button you click.
JobA group of steps that run together on one fresh computer. Different jobs run side by side.
Runner (runs-on:)The temporary computer GitHub lends the job. It starts empty, with no copy of your code.
StepOne thing to do, in order. Either run a command (run:) or use a ready-made action (uses:). If a step fails, the job stops.
ActionA step someone else already wrote, like "download the repo" or "deploy to Azure".

Where to watch it work: your repository's Actions tab shows every run, with a green check or a red X.

2. YAML in two minutes

Workflows are written in YAML, a format that is picky about spacing. Learn these four rules and you will avoid most errors:

  1. Indentation means nesting. Use spaces, never the Tab key. Two spaces per level is standard. A line indented under another belongs to it.
  2. key: value sets a setting. There must be a space after the colon.
  3. A dash starts a list item. A list of steps is a column of lines that each begin with - .
  4. A line starting with # is a comment for people; GitHub ignores it. The examples below use comments to explain themselves.

If the spacing is wrong, GitHub won't even start the run. The Actions tab shows "Invalid workflow file" with the line number to fix.

3. Your first workflow

Start tiny so you can see the pieces work. Create .github/workflows/hello.yml:

name: Hello                  # the name shown in the Actions tab

on: push                     # run every time someone pushes

jobs:
  say-hello:                 # a job; you choose its name
    runs-on: ubuntu-latest   # the computer to use: a fresh Linux machine
    steps:
      - run: echo "Hello from GitHub Actions"     # one step: run a command
  1. Save the file, then commit and push it.
  2. Open the Actions tab. A run named Hello appears within seconds.
  3. Click the run, click the say-hello job, and open the step. You will see your message in the log.

You now know the whole pattern: a trigger starts a job; the job runs steps on a runner. Delete hello.yml when you are done.

4. Check every push (CI)

Continuous integration (CI) means a robot checks every change before it can cause harm. Ours will lint (proofread), test, and build both halves of the app, so you find a mistake in seconds instead of after a failed deployment. Create .github/workflows/ci.yml: 

name: CI

on:
  push:            # run on every push to any branch
  pull_request:    # and on every pull request

jobs:
  frontend:                                # job 1: checks the website code
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend        # run every command inside the frontend/ folder
    steps:
      - uses: actions/checkout@v7          # download your repository onto the empty runner

      - uses: actions/setup-node@v7        # install Node.js on the runner
        with:
          node-version: '24'               # use Node 24, the version this course uses
          cache: npm                       # remember downloaded packages to go faster next time
          cache-dependency-path: frontend/package-lock.json

      - run: npm ci                        # install exactly what package-lock.json lists
      - run: npm run lint                  # proofread the code
      - run: npm test                      # run the tests
      - run: npm run build                 # make sure the site builds

  backend:                                 # job 2: checks the server code (runs at the same time)
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: npm
          cache-dependency-path: backend/package-lock.json

      - run: npm ci
      - run: npm run lint
      - run: npm test

Why each choice

  • actions/checkout comes first because the runner starts empty. Without it, there is no code to test.
  • npm ci, not npm install. ci installs exactly the versions in package-lock.json, so the robot and your laptop test the same thing. If it fails with a lock file error, run npm install on your computer and commit the updated package-lock.json.
  • working-directory saves you from typing cd frontend before every command. If a step fails with "package.json not found", this line is almost always wrong.
  • Two jobs, not one. They run side by side and report separately, so you can see at a glance whether the frontend or the backend is the problem.
  • Run the same commands on your computer first. If npm run lint and npm test don't pass locally, they won't pass in CI.
Does your project have a lint script or tests? A step that runs a script that doesn't exist fails. If your project has no tests yet, delete that line rather than faking one, and add tests when you can. Check your package.json "scripts" section.

5. Secrets and variables

The deploy workflows need things you must not put in your code: passwords for uploading to Azure. GitHub stores them outside your code, in two kinds of place:

Secret

Hidden and encrypted. After you save it, nobody (including you) can read it again, and it is blanked out of logs. Use it for anything that works like a password.

Variable

Plain and visible. Use it for settings that are not sensitive, such as the name of your Azure app.

You add both in your repository under Settings → Secrets and variables → Actions (secrets on one tab, variables on the other). The workflows below use these names. They must match exactly, including capitals.

NameKindValueWhere to get it
APP_SERVICE_PUBLISH_PROFILESecretThe whole contents of a fileAzure portal → your App Service → Overview → Download publish profile. Open the file in a text editor, copy everything, then delete the downloaded file. (If the button is greyed out, ask your instructor to turn on basic authentication.)
AZURE_WEBAPP_NAMEVariableYour App Service's nameThe name at the top of the App Service page.
AZURE_STATIC_WEB_APPS_API_TOKENSecretA long tokenAzure portal → your Static Web App → Overview → Manage deployment token → copy.
VITE_BACKEND_API_URLSecretYour backend's web address, with no slash at the endAzure portal → your App Service → Overview → Default domain. Copy it exactly, add https:// in front. Don't guess it: new apps can have a random suffix.
Never paste a publish profile, token, or password into your code, a chat, an AI tool, or a commit. A secret that reaches GitHub in a file is public the moment it is pushed, and deleting the file later doesn't remove it from history. If one leaks, replace it in Azure and update the secret.

Who can do this? Only a repository Admin can open the Settings tab. Keep Admin to one teammate; everyone else works with Write access and can still use the secrets through the workflows.

6. Deploy the backend

This workflow uploads your backend/ folder to your Azure App Service whenever backend code changes on main. Create .github/workflows/deploy-backend.yml: 

name: Deploy backend (App Service)

on:
  push:
    branches: [main]                 # only deploy from the main branch
    paths:                           # ...and only when these files changed
      - 'backend/**'
      - '.github/workflows/deploy-backend.yml'
  workflow_dispatch:                 # also add a "Run workflow" button in the Actions tab

concurrency: deploy-backend          # never run two backend deployments at once

jobs:
  build-test-deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read                 # the job may read the repo and nothing more
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          node-version: '24'         # keep this equal to the Node version set on the App Service
          cache: npm
          cache-dependency-path: backend/package-lock.json

      # Fail early, with a clear message, if a setting was forgotten.
      - name: Check repository settings
        env:
          APP_NAME: ${{ vars.AZURE_WEBAPP_NAME }}
          HAS_PROFILE: ${{ secrets.APP_SERVICE_PUBLISH_PROFILE != '' }}
        run: |
          [ -n "$APP_NAME" ] || { echo "::error::Repository variable AZURE_WEBAPP_NAME is not set"; exit 1; }
          [ "$HAS_PROFILE" = "true" ] || { echo "::error::Repository secret APP_SERVICE_PUBLISH_PROFILE is not set"; exit 1; }

      - run: npm ci
      - run: npm test                # a failing test stops the deployment, so broken code never ships

      - name: Remove dev-only packages before upload
        run: npm prune --omit=dev    # the server doesn't need lint or test tools

      - name: Deploy to Azure App Service
        uses: azure/webapps-deploy@v3
        with:
          app-name: ${{ vars.AZURE_WEBAPP_NAME }}                       # which Azure app to update
          publish-profile: ${{ secrets.APP_SERVICE_PUBLISH_PROFILE }}   # the password to upload with
          package: backend                                              # which folder to upload

The new ideas

  • on: push: branches / paths. Without paths, every push (even a typo fix in the README) would redeploy the backend.
  • workflow_dispatch. Adds a Run workflow button, so you can deploy right after setting up Azure without making a fake commit.
  • ${{ vars.NAME }} and ${{ secrets.NAME }}. This is how a workflow reads a variable or a secret. The value is filled in at run time and never appears in the file.
  • The "Check repository settings" step turns a confusing Azure error into a plain message such as "Repository secret APP_SERVICE_PUBLISH_PROFILE is not set".
  • npm test before the deploy. If a test fails the job stops, so broken code is never uploaded.
  • concurrency. If two pushes land close together, the second waits for the first, so the two uploads can't collide.
  • Your Azure app must have the matching settings first (database address, JWT_SECRET, FRONTEND_URL, NODE_ENV=production). The workflow uploads code; it does not set these. See the backend README.

First deploy: Actions tab → Deploy backend (App Service) → Run workflow (choose the main branch in the small menu, then click the green button). The button only appears once the workflow file has been pushed to your default branch. Then open https://<your default domain>/health. The very first request can take a minute or more while the app wakes up (a "cold start"); after that it answers in a fraction of a second with {"ok":true,"env":"production"}.

7. Deploy the frontend

The frontend is built in the workflow and the finished site is uploaded to your Static Web App. Create .github/workflows/deploy-frontend.yml: 

name: Deploy frontend (Static Web Apps)

on:
  push:
    branches: [main]
    paths:
      - 'frontend/**'
      - '.github/workflows/deploy-frontend.yml'
  workflow_dispatch:

concurrency: deploy-frontend

jobs:
  build-test-deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: npm
          cache-dependency-path: frontend/package-lock.json

      - name: Check repository settings
        env:
          VITE_BACKEND_API_URL: ${{ secrets.VITE_BACKEND_API_URL }}
          HAS_TOKEN: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN != '' }}
        run: |
          [ -n "$VITE_BACKEND_API_URL" ] || { echo "::error::Repository secret VITE_BACKEND_API_URL is not set"; exit 1; }
          case "$VITE_BACKEND_API_URL" in */) echo "::error::VITE_BACKEND_API_URL must not end with /"; exit 1;; esac
          [ "$HAS_TOKEN" = "true" ] || { echo "::error::Repository secret AZURE_STATIC_WEB_APPS_API_TOKEN is not set"; exit 1; }

      - run: npm ci
      - run: npm test

      - name: Build
        run: npm run build
        env:
          # Vite copies this value INTO the built website files, so it must be set while building.
          VITE_BACKEND_API_URL: ${{ secrets.VITE_BACKEND_API_URL }}

      - name: Deploy to Azure Static Web Apps
        uses: Azure/static-web-apps-deploy@v1
        with:
          azure_static_web_apps_api_token: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN }}
          action: upload
          app_location: frontend/dist     # the finished site, relative to the repo root
          skip_app_build: true            # we already built it above; don't let Azure build again

The new ideas

  • The backend address is baked in at build time. VITE_BACKEND_API_URL is copied into the website files when you run npm run build. Changing the secret later does nothing until you build and deploy again.
  • No slash at the end of that address. The app adds paths such as /auth/login itself, so https://x.net/ would become https://x.net//auth/login.
  • app_location: frontend/dist with skip_app_build: true means "upload this finished folder as it is".
  • frontend/public/staticwebapp.config.json must exist. It makes refreshing a page such as /map work instead of showing "404 Not Found".
  • Only one workflow should deploy the frontend. If Azure also created its own workflow file in your repo, delete one of them, or both will run.

Check it: open your Static Web App's URL, open the browser's developer tools (F12 → Console), and look for the line Frontend API Base URL: …. It must show your Azure backend, not localhost.

9. When a run fails

A red X is information, not a disaster. Read it in this order:

  1. Open the Actions tab and click the failed run.
  2. Click the job with the red X (for example backend).
  3. Find the step with the red X and click it open. The last lines of that step say what went wrong. Read them before you change anything.
  4. Fix it, commit, and push. A new run starts on its own.
What you seeLikely causeFix
"Invalid workflow file" and a line number A YAML spacing mistake (often a Tab, or a missing space after a colon) Fix the line named; use spaces only.
"No such file or directory" or "package.json not found" Wrong working-directory or folder name Match the folder names in your repo exactly; they are case-sensitive on the runner.
npm ci fails with a lock file message package.json and package-lock.json disagree Run npm install locally and commit the updated lock file.
"Missing script: lint" (or test) Your package.json has no script with that name Add the script, or remove that step.
A test fails only in GitHub It depends on something on your laptop (a .env, a local database) Make the test self-contained; the runner has none of your files that aren't in Git.
"Repository secret ... is not set" A secret is missing or its name differs by even one letter or capital Re-check the table in section 5.
The deploy step says authentication failed An old or wrong publish profile or token Download a fresh one from Azure and replace the secret.
Green run, but the site still shows old behavior Your browser cached the old page, or the app is still waking up Hard-reload (Ctrl+Shift+R). For the backend, wait a minute and try /health again.
Green run, but the map's background is grey boxes saying "Access blocked" The site tells the browser not to send a Referer header, and OpenStreetMap requires one Set referrerPolicy="strict-origin-when-cross-origin" on the map's TileLayer and add a Referrer-Policy header in staticwebapp.config.json. The reference app does both.

10. Keep it safe

  • Secrets live only in GitHub's Secrets tab and Azure's settings, never in a file you commit. Run git status before every git add and check that no .env file is listed.
  • Least privilege. One Admin; everyone else has Write. The deploy workflows ask for permissions: contents: read, only what they need.
  • Know what you use. Actions are written like actions/checkout@v7. The @v7 means "version 7 and its later fixes", so the action's authors can still update it under you. Stick to actions from GitHub (actions/…) and Microsoft (azure/…, Azure/…), and read an action's page before adding a new one.
  • Pull requests from forks don't receive your secrets. That is a safety feature, so don't try to work around it.

11. Checklist

  • I understand a workflow is a trigger, jobs, and steps, and I can explain what actions/checkout is for.
  • ci.yml is green on main: lint, test, and build pass for both folders.
  • The three secrets and one variable exist with exactly the names in section 5.
  • The backend deploy is green and /health returns {"ok":true,"env":"production"}.
  • The frontend deploy is green and the console shows my Azure backend as Frontend API Base URL.
  • I can register, log in, refresh on /map, fetch a month of data, and log out on the live site.
  • No secret appears in any file in my repository.
