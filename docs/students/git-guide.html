Git is your team's safety net, if you use it the same way every time

Git remembers every version of your project and lets several people change it at once without overwriting each other. It only works smoothly when everyone follows the same routine. This guide gives you that routine twice: with commands in the terminal, and with VS Code's built-in Source Control buttons. Both do exactly the same thing, so use whichever you like, and mix them freely.

Before you start: Git is installed and your name and email are set, and your team has a repository you can clone. All of that is in the Sprint 1 guide. New words are in the Glossary.
The golden rule: never write code directly on main. Always work on your own branch, and bring it into main only when it works.

1. What Git is and how repositories work

The problem Git solves

You have probably saved a file as report_final.docx, then report_final_v2.docx, then report_REALLY_final.docx. Now imagine four people editing the same project at once. Who has the newest copy? Whose change overwrote whose? Git exists to answer those questions. It is a version control system: a program that remembers every saved version of your project, who made each change and why, and lets you go back to any of them or combine several people's work.

What a repository is

A repository (or repo) is your project folder plus its history. The history lives in a hidden folder named .git inside the project folder. You never edit anything in .git by hand, and you must not delete it: delete .git and the folder is just ordinary files again, with the history gone. 

cs330-2025-group07/        <- the repository (your project folder)
├── .git/                  <- hidden: the whole history lives here
├── .gitignore             <- a list of files Git should never track
├── README.md
├── frontend/
└── backend/
  • The files you see and edit are the working directory: one version of the project, the one you are working on right now.
  • Everything else, every earlier version, is stored compactly in .git.
  • .gitignore lists things Git should leave alone: node_modules/ (huge, and rebuilt by npm install), .env (secrets), build output. Anything not ignored can end up on GitHub.

Commits are snapshots

When you commit, Git saves a snapshot of your whole project at that moment, together with your name, the time, and a message that says why. Each commit has a long unique ID (a hash, shown shortened, like a96de47) and remembers which commit came before it. So your history is a chain: 

  C1 <--- C2 <--- C3 <--- C4        each commit points back to its parent
                      ^
                    main              a branch is just a label on one commit

Because every commit is a complete snapshot, you can look at, compare with, or return to any of them.

Every copy is a full copy

Git is distributed. When you clone a repository, you don't just download the latest files: you get the entire history. That means you can commit, branch, and read history with no internet, and every teammate's computer holds a complete backup. The copy on GitHub is simply the one everyone agrees to share, called the remote and nicknamed origin. 

        GitHub: the shared copy ("origin")
            ^   |
     git push   |  git fetch / git pull
            |   v
   +----------------+   +----------------+   +----------------+
   |  Alice's repo  |   |   Bob's repo   |   |  Chen's repo   |
   | (full history) |   | (full history) |   | (full history) |
   +----------------+   +----------------+   +----------------+
   each person edits their own working directory

Nothing you do on your computer reaches your teammates until you push, and nothing they do reaches you until you pull (or fetch). That separation is what makes Git safe: you can experiment freely, then share only when the work is ready.

The four places your work lives

Almost every Git confusion goes away once you can picture where your work is:

PlaceWhat it isYou move work in with
Working directoryThe files you see and edit.Typing code
Staging areaA loading dock: the changes chosen for the next commit.git add (the + in VS Code)
Local repositoryYour permanent history on your computer: commits and branches.git commit
Remote (origin)The copy on GitHub that your team shares.git push up, git fetch / git pull down

The staging area is the part beginners find odd. It exists so that you choose exactly what goes into each commit, instead of saving every edited file every time. That keeps commits small and focused, and keeps a half-finished file or a secret out of the history.

Branches

  • A branch is a separate line of work. Making one is instant and free, because it is just a new label on a commit. main is the branch your team treats as "the working version".
  • HEAD means "where you are now": usually the branch you have checked out.
  • Branches you create are local until you push them. Your teammates can't see them yet.
  • A pull request (PR) is GitHub's way of saying "please review my branch and merge it into main".
main or master? Same idea, different name. Repositories created on GitHub today call the default branch main; older ones call it master. This guide says main. Run git branch to see what yours is called, and use that name in every command.

Try it for two minutes: a repository of your own

Nothing here touches GitHub or your project. Make a practice folder and watch the pieces appear:

git init -b main practice        # create a new repository in a folder named practice
cd practice
echo "# My notes" > notes.md       # make a file
git status                       # notes.md is "untracked": Git sees it but isn't recording it
git add notes.md                 # stage it (move it onto the loading dock)
git commit -m "Add notes"        # snapshot it (your first commit)
echo "second line" >> notes.md    # change the file
git diff                         # shows exactly which line changed
git commit -am "Add a second line"   # stage and commit changes to tracked files in one step
git log --oneline                # your history: two commits, newest first

git log --oneline prints one line per commit, newest first. Run git status after every command and read what it says: it tells you what Git thinks is going on, and what to do next. When you are done, delete the practice folder; it was only for learning.

First time using Git on this computer? Git needs your name and email to label your commits. Run the two git config --global commands in the Sprint 1 guide once.

2. The daily workflow

Follow these steps every time you start a piece of work. Run them in the VS Code terminal (Ctrl+\`) in your project folder.

A. Start from an up-to-date main

git checkout main        # go to the main branch (or: git switch main)
git pull                 # get your teammates' latest work

Once your local main is up to date, do not change it directly.

B. Make your own branch and write code

git checkout -b <branch-name>     # create the branch and switch to it (or: git switch -c <branch-name>)

Name it for the job, such as feature/login-page or fix/map-colors. Both main and your new branch exist only on your computer so far. Now write code. Save often, and commit small, finished pieces: 

git status                         # what changed?
git add <file>                      # stage a file (or: git add .  for everything)
git commit -m "feat: add login form"   # snapshot what you staged, with a message

C. Keep up with your team (rebase)

Your teammates keep merging into main while you work. Every so often, bring their changes under your work. This is called rebasing: it replays your commits on top of the newest main. 

git checkout main
git pull
git checkout <branch-name>
git rebase main

Commit or stash first. If you have uncommitted edits, Git can refuse even the first git checkout main (it won't overwrite your work) and will always refuse to rebase. Either commit them, or stash them (set them aside) before you start, and bring them back at the end: 

git stash                  # set your uncommitted edits aside
git checkout main
git pull
git checkout <branch-name>
git rebase main
git stash pop              # bring your edits back

D. Sanity check before you share

When your branch is finished, make sure it contains your work and nothing else:

git status                        # nothing unexpected? everything committed?
git checkout main
git pull
git checkout <branch-name>
git rebase main                   # on top of the very latest main
git diff main --name-only         # the ONLY files listed should be ones you meant to change

If a file appears that you didn't mean to touch, stop and fix it before going on (see undoing things).

E. Finish: choose one of two ways

Option 1: Pull request (recommended)

git push -u origin <branch-name>

Then on GitHub click Compare & pull request, describe the change, and ask a teammate to review and merge. This is what the Sprint 1 guide practices. It keeps a second pair of eyes on main.

Option 2: Merge locally, then push main

git checkout main
git merge --no-ff <branch-name>
git push origin main

Use this only if your team or instructor says so. --no-ff always records a merge commit, so the history shows which commits belonged to your feature. It fails if main is protected (see "Locked main" in section 8); then use Option 1.

Afterwards, tidy up and start the next job from step A:

git checkout main
git pull
git branch -d <branch-name>                 # delete the finished local branch
git push origin --delete <branch-name>      # delete it on GitHub too (if you pushed it)

3. Notes on the workflow

The routine above is the one most professional teams use. These details trip people up:

  • git add comes before git commit. A commit only includes what you staged. Quote the message: git commit -m "your message". git commit -am "message" stages changes to files Git already tracks, but never new files.
  • Commit before you rebase, and before you switch branches. A rebase needs a clean working directory, and switching branches can fail when your uncommitted edits would be overwritten. Stashing is the fallback for work you are not ready to commit.
  • Only rebase a branch that is just yours. Rebasing rewrites your commits. If you already pushed the branch and others use it, rebasing forces everyone else to untangle it. If you must rebase a branch you pushed (for example, your own pull request), update GitHub with git push --force-with-lease, which refuses to overwrite work you haven't seen. When in doubt, use git merge main on the branch instead: it is always safe.
  • A rebase can stop with conflicts. Git pauses, you fix the files (section 5), then git add them and run git rebase --continue. To give up and go back to how things were: git rebase --abort.
  • Use git pull --ff-only on main if you like safety. It stops instead of creating an accidental merge commit when your local main has stray commits.
  • git checkout versus git switch. checkout does many jobs; newer Git splits them: git switch changes branches and git restore restores files. Use either. The two forms are interchangeable for branches.
  • Pushing straight to main skips review. That is fine for a tiny solo project and risky for a team. Many teams, and GitHub itself, can protect main so only pull requests may change it.

Which should you use? The buttons are easiest for the everyday loop (stage, commit, sync). The terminal is clearer for anything unusual (rebase, stash, undo) because you can see exactly what Git says. Whatever you click, VS Code runs the same Git commands, and you can see them in Output → Git. Beginners often learn fastest by doing the same thing both ways once.
"Sync Changes" is a pull and a push. It is handy, but on main it will also try to push your local commits, and by default it merges rather than rebases. Switch to your own branch first, and read the message before you confirm.

5. Merge conflicts

A conflict happens when you and a teammate changed the same lines. Git can't guess whose version wins, so it stops and asks you. It is normal, not a disaster. Git marks the file like this: 

<<<<<<< HEAD
const title = 'Weather Map';          // the version on the branch you are on
=======
const title = 'Temperature Map';      // the version coming in
>>>>>>> feature/rename
  1. Find the conflicted files: git status lists them as both modified. In VS Code they show a ! and sit under Merge Changes.
  2. Decide what the final text should be. Keep one side, the other, or a mix. Talk to your teammate if you are unsure.
  3. Edit the file so no <<<<<<<, =======, or >>>>>>> lines remain. In VS Code, click Accept Current Change, Accept Incoming Change, or Accept Both Changes above the conflict, or use the Resolve in Merge Editor button for a three-pane view, then Complete Merge.
  4. Test it. Run the app and npm test. A conflict resolved wrongly still compiles sometimes.
  5. Tell Git it is resolved: 
    git add <file>
git rebase --continue      # if you were rebasing
# or: git commit           # if you were merging

Changed your mind halfway? git rebase --abort or git merge --abort puts everything back as it was. To have fewer conflicts: commit small, pull often, and tell teammates which files you are editing.

6. Undoing things

Git makes it hard to lose committed work, so most mistakes are fixable. Match your situation:

SituationCommandWhat it does
Staged the wrong file (not committed)git restore --staged <file>Moves it back out of the staging area. Your edits stay.
Want to throw away edits to a filegit restore <file>Resets the file to the last commit. The edits are gone for good.
Typo in the last commit message, or forgot a filegit commit --amendRewrites the last commit. Only before you push it.
Undo the last commit but keep the workgit reset --soft HEAD~1Removes the commit; the changes stay staged. Only before you push it.
Undo a commit that is already pushedgit revert <commit>Adds a new commit that cancels the old one. Safe for shared history.
Set unfinished work asidegit stash and git stash popSaves your edits, gives a clean directory, restores them later.
Committed on main by mistake (not pushed)git branch <new-branch>, then git reset --hard origin/mainSaves the commits on a new branch, then puts main back. Check git status first.
"I lost a commit!"git reflogA log of everywhere HEAD has been. Find the commit and git switch -c rescue <hash>.
Two commands to treat with respect. git reset --hard and git restore <file> discard uncommitted work with no undo. And never rewrite history that others have already pulled (--amend, reset, rebase on a shared branch): use git revert instead.

Committed a secret (a password, key, or .env)? Deleting it in a later commit does not remove it from history. Treat the secret as public: change it at its source first, then ask your instructor how to clean the repository. Prevent it with a correct .gitignore and by checking git status before every git add (see the Sprint 1 guide).

7. Moving commits around

You won't need these every day, but they appear in real projects and in the practice exercises (section 10).

IdeaCommandWhen it helps
Relative referencesHEAD~1 (one commit back), HEAD~3, main^ (parent of main)Name a commit by its position instead of its long ID. git log --oneline shows the IDs.
Detached HEADgit checkout <commit>Look around at an old version. You are on no branch, so new commits can get lost. Get back with git switch main, or keep your work with git switch -c new-branch.
Move a branch labelgit branch -f main HEAD~3Point a branch at a different commit.
Cherry-pickgit cherry-pick <commit>Copy one commit from another branch onto yours, without merging the whole branch.
Interactive rebasegit rebase -i HEAD~4Clean up your unpushed commits before sharing: reorder, reword, squash several into one, or drop one.
Tagsgit tag v1.0 <commit>, git describeA permanent, readable name for a milestone (such as the version you hand in). A tag never moves, unlike a branch.
Merge vs rebasegit merge / git rebaseMerge keeps history as it happened and adds a merge commit. Rebase replays your commits for a straight line. Both combine work; choose by your team's rule.

8. Remotes and pull requests

A remote is another copy of the repository, almost always the one on GitHub, nicknamed origin. Your computer also keeps a read-only note of where each remote's branches were the last time you looked, named origin/main (a remote-tracking branch).

CommandWhat it does
git clone <url>Copies a repository from GitHub to your computer and sets origin.
git remote -vShows which address origin points to.
git fetchDownloads new commits and updates origin/main, but does not change your branches or files. Always safe.
git pullA fetch followed by a merge into your current branch. git pull --rebase rebases instead.
git pushUploads your branch's commits. The first time use git push -u origin <branch>, which also remembers the link.
git branch -vvShows each local branch, the remote branch it tracks, and whether you are ahead or behind.

"Diverged history" and rejected pushes

If a teammate pushed while you were working, git push is rejected (fetch first, non-fast-forward, or failed to push some refs). Git is protecting their work. Fix it by bringing their commits in, then pushing again: 

git fetch
git rebase origin/main     # or: git pull --rebase   (on your own branch)
git push

"Locked main": why you can't push to it

A repository admin can protect main so that nobody pushes to it directly, and every change must arrive through a reviewed pull request. If git push origin main says the branch is protected, that is working as intended. Push your branch, open a pull request, and let a teammate review and merge it. This is also why only one teammate should be Admin and the rest have Write access (see the Sprint 1 guide).

A good pull request

  • One purpose, small enough to review in a few minutes.
  • A title and short description that say what and why.
  • Your branch is rebased or merged up to date with main, and tests pass (the CI check turns green).
  • You re-read your own diff first, looking for debugging leftovers and anything secret.
  • The reviewer is a different teammate. Fix their comments with more commits on the same branch.

10. Practice: Learn Git Branching

Reading about Git only goes so far. Learn Git Branching is a free, visual, interactive site that draws the commit graph as you type real Git commands, so you can see what a rebase or a cherry-pick does. Open it, choose Levels, and work through the Main tab in order, then the Remote tab. This table says where each group of levels matches this guide:

Quiz 9 asks you to complete this activity. The assignment on eCampus is the official version and no points are given unless you follow its directions exactly, so reread it before you submit. In summary:
  • Complete the first 10 levels of the Main tab and the first 8 levels of the Remote tab. The tables below show which levels those are.
  • Take one screenshot of your final progress and paste it into a document. It must show (1) the browser's address bar with the URL, (2) the image showing your completed levels, and (3) something that identifies you, such as your operating system account or your email tab.
  • Each additional level you finish beyond those earns bonus credit (0.5 point each, up to 8 points), so completing all of them is worth doing.

Taking the screenshot

  1. Finish the levels. Then click Levels so the level picker shows your progress, switching between the Main and Remote tabs as needed.
  2. Make the browser window show the address bar. Don't crop it out, and don't use a screenshot of only the page.
  3. Make sure something that identifies you is in the picture: the account name in your taskbar, your OS user menu, or an open email tab. Show only what is needed to identify you. Never include a password or other private information.
  4. Take the screenshot (Win+Shift+S on Windows, Cmd+Shift+4 on macOS), paste it into your document, and zoom in to check that the URL and your name are readable.

If your screenshot needs both tabs to show everything, ask your instructor whether to submit one image or two before you submit, not after.
